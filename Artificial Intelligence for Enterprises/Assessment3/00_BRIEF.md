## 一、場景(Kenny 任職公司,**寫作時一律匿名**)

### 產品與規模

- 車隊管理系統,核心是**車載 AI 攝影機(行車記錄器,以下稱 edge 裝置)**做事件偵測
- **多個車隊客戶**,每個車隊底下**上千至上萬台**裝置
- **每台裝置每天產生至少 10–20 個 event**
- ⚠️ 精確台數、精確 event 量、精確準確率**待 Kenny 提供量級**(見 §六 待填槽)

### 現行三階段架構(**這是公司相對競爭者的差異化,寫作時抽象化為「兩階段推論 + 人工校驗」,不指名公司、不寫硬體規格與門檻值**)

```
第一階段  edge 裝置端 AI 初判
   ↓ 初判結果上傳
第二階段  伺服器端 AI 複判 → 判定屬實 = 完整 event → 回傳裝置,向駕駛廣播警示
   ↓ 複判仍有誤報
第三階段  人工第三次認證(工讀生 + 派遣人員)→ 標註結果回頭訓練下一版模型
```

**競爭者的路線**:把更強的硬體塞進 edge 裝置,靠算力硬扛。
**本公司的路線**:edge 輕量初判 + server 複判。代價就是第三階段那批人。

### 現況痛點

第三階段是**長期常態工作流**,不是專案。目前**每一筆複判結果都送人工看**,
依靠大量工讀生與派遣人員進行「第三次誤報分析」,再把校正後的標註回灌訓練下一版模型。

## 二、v4 的論證主線(骨幹,細節由設計階段決定)

### 🔑 因果閉環 —— 這是本案最強的敘事資產

老師 8/4 明訂因果鏈不可跳段:**壓力 → 對企業的影響 → 需要增強的能力 → AI 項目 → 實施步驟 → KPI**。
本案可以串成一條**會自我惡化的迴路**,比線性因果更有力:

```
裝機量成長 → 第三階段複核量線性成長 → 人力吃緊、流動率高
   → 標註品質不穩 → 回流訓練資料品質不穩 → 下一版模型校正變慢
   → 誤報率降不下來 → 複核量繼續成長 ⟲
```

**加人只是讓迴路轉得更久,不會讓它停。** 這句話同時答完「為何要現在做」與「為何不能靠加人解決」。

### 能力缺口的定義

**不是**「更準的模型」,**是「模型知道自己哪裡沒把握」的能力(信心校準)**。
這句話把本公司和「堆硬體的競爭者」切開:他們買算力,我們買分流。

### 成本不對稱(A2a 已用過同一套論證並拿滿分,可搬)

| 錯誤類型 | 代價 |
|---|---|
| FP — 把誤報當成要複核的 | 浪費第三階段人力 → **可直接換算成錢** |
| FN — 把真事件當成誤報濾掉 | 🔴 **駕駛沒收到警示 = 行車安全事件** |

不對稱的方向是**安全**,不是損失利差。這比金融案例的利差有力得多。

## 三、🔴 已知的設計缺陷 —— 必須修掉,否則答辯會被打穿

Kenny 初步構想是:

```
高信心真事件 → 直接放行
高信心誤報   → 直接丟棄     ← 這一條在安全場景站不住
只有沒把握的 → 送人工
```

**問題**:提案自己剛論證完「FN 的代價是行車安全」,又主張「高信心誤報直接丟棄」——
只要跑得夠久,一定會有一次高信心地丟掉真的碰撞事件。這是**提案的內部矛盾**,不是小瑕疵。

**必須改成三道閘(或提出更好的設計):**

1. **事件類型硬分層** —— 安全紅線類事件**無論信心多高都不自動丟棄**;
   自動分流只作用在成本有界的類別。
   🔴 **哪些類別屬於哪一邊 = `[[待填-4]]`,Kenny 尚未提供。**
   ⚠️ 本檔初版曾以「碰撞 / 前車追撞預警 / 駕駛失能」與「遮擋 / 鏡頭髒污 / 光影誤觸發」
   當作例子,**那是撰寫者從行車記錄器產業常識補的佔位示意,不是 Kenny 給的事實**。
   凡是沿用那些類別名的產出,一律視為佔位,回填前不得寫進交件物
2. **被丟棄流的抽樣稽核** —— 固定比例回抽人工看,持續量測「自動丟棄流的真事件漏放率」。
   這個數字本身就是最重要的 KPI,而且讓「我們知道自己錯多少」變成可證明的
3. **shadow mode 先跑** —— 前 N 週分流器只記錄不動作,拿建議與人工實際判定比對。
   不影響現況,又能在專案結束前交出真實數字

改完之後這一頁從最弱變最強:同時展示風險意識、量化能力與落地路徑。

### ⚠️ 但三道閘本身也被打回過(2026-08-08 評審意見,必須一併處理)

> **三道閘沒有消滅內部矛盾,只是把它搬家。**
> 事件類型判錯 → 一個真的安全事件被歸進「成本有界」類別 → 然後被高信心自動處理。
> 漏放從**模型層**被推到**流程層**,而流程層的漏放**沒有信心分數可回溯、
> 不會進模型評估報表** —— 對評分者(研究對抗魯棒性)而言,這比原本那條矛盾更糟,
> **因為它不可觀測**。

「事件類型硬分層」預設了類型判斷本身可靠,但**類型判斷也是模型做的**。
→ 任何最終設計都必須回答:**流程層的漏放怎麼被看見?** 沒有答案就不要寫進提案。

同一輪還有一條:**「清單誰都會列,順序騙不了人。」**
工作包裡若把「開閘」排在「投毒/標註品質防護」之前,逐週對照就查得出來。
**治理必須先於重訓,開閘必須後於防護。**
