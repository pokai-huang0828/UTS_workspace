## 3.2 機器學習產品要求 ⭐（A2「基於 ML 的解決方案」20 分的正課）

> 承接單元一 §1.6 的五個關鍵因素，**這裡逐項展開得詳細很多**。

**為什麼要明確要求**：
- 沒有清晰要求，就很難設計、開發、部署一個能有效解決目標問題的 ML 系統
- 有助於**識別並排定優先級**：系統特徵、功能、效能指標
- 讓利害關係人**就專案目標達成一致、促進溝通**
- **管理各方預期**，降低專案失敗或與業務目標不一致的風險

---

### 要求一：商業價值（兩個子項）

| 子項 | 要評估什麼 |
|---|---|
| **利害關係人目標一致** | 確保產品與相關方（**客戶、合作夥伴、員工、股東**）的目標與價值觀一致。評估對**滿意度、參與度、忠誠度**的影響 |
| **競爭優勢** | 是否能讓組織相較同市場其他組織獲得競爭優勢。評估對**市場份額、品牌聲譽、客戶忠誠度**的影響 |

---

### 要求二：技術可行性（五個子項）⭐

**定義**：產品能否在**現有技術基礎設施中實施、整合、維護**。

| 子項 | 要檢查什麼 |
|---|---|
| **相容性**（Compatibility） | 與現有**硬體、軟體及其他技術組件**是否相容；是否需要當前無法輕易獲得的特定配置 |
| **可擴展性**（Scalability） | 能否**擴大或縮小規模**；資料量或使用者數量增加的影響；能否處理增加的負載 |
| **安全性** | 是否符合組織的安全要求；評估**資料隱私與安全漏洞**的潛在風險 |
| **整合**（Integration） | 與現有系統及流程整合的**難易度**；是否需要額外工具；是否與 **API** 或其他整合方法相容 |
| **維護與支援** | **軟體更新、錯誤修復**等維護活動；組織**是否具備所需技術專業能力**，或需要外部支援 |

> 🎯 **Bank X 對應**：資料已在 CRM／核心銀行系統（相容性 ✓）；表格式分類模型運算需求低（可擴展性 ✓）；
> 但**金融資料的安全性與隱私**是重點；整合到既有呼叫中心系統（CTI）是關鍵。

---

### 要求三：資料品質（五個子項）⭐

**核心目標**：確保用**能準確反映目標總體、流程或系統的高品質資料**訓練與驗證，
**降低錯誤、偏差、不準確性**對效能造成負面影響的風險。

| 子項 | 要評估什麼 |
|---|---|
| **資料相關性** | 資料是否**與要解決的業務問題相關**；能否準確反映**目標總體** |
| **資料完整性** | 是否包含有效訓練與驗證所需的**全部相關變數、記錄、觀測值**；是否**缺少關鍵變數或記錄** |
| **資料準確性** | 是否包含**錯誤、噪聲、異常值**；是否已預處理／轉換／清理以消除不準確或不一致 |
| **資料一致性** | 來自**不同來源、不同格式、不同時期**的資料是否一致；是否有**差異、重複項、不一致** |
| **資料偏差** | 是否存在偏差、模型是否會**偏向特定變數／群體／結果**；資料能否**代表目標總體**；是否已識別並處理潛在偏差 |

> 🎯 **Bank X 對應（每一項都有話可寫）**：
> - **相關性** ✓ 目標組／對照組實驗設計完整
> - **完整性** ⚠️ 70,638 個缺失值，但是**結構性缺失**（對照組未被撥打），要說明
> - **準確性** ⚠️ `duration` 對照組結構性為 0，是設計而非錯誤
> - **一致性** ✓ 單一來源
> - **偏差** ⚠️ `age`／`job`／`marital`／`education` 都是敏感屬性

---

### 要求四：模型效能（四個子項）⭐

**定義**：模型質量 = 依評估指標衡量的 ML 模型品質。

| 子項 | 定義與要點 |
|---|---|
| **準確率／正確性**<br>Accuracy / Correctness | 確保模型能以較高準確率預測結果；⭐ **考慮模型在不同資料集、不同時期、不同子群體中的準確性是否一致** |
| **泛化能力／相關性**<br>Generalisation / Relevance | 確保在**新的未見資料**上保持良好表現，降低**過擬合或欠擬合**的風險；是否用**多樣且具代表性**的資料訓練與驗證 |
| **穩健性**<br>Robustness | ⭐ **與正確性／相關性不同，穩健性是一項「非功能特性」**。衡量方法：**檢查系統在存在噪聲的情況下能否保持正確性**。噪聲可能是**異常值**，或**資料中導致模型作出錯誤預測的細微變化** |
| **延遲／效率**<br>Latency / Efficiency | 系統的**構建速度或預測速度**。⭐ 原文重點：「隨著資料量與系統複雜度呈指數級增長，**效率已成為選擇模型與框架時的重要特性，有時甚至比準確率更加重要**」 |

---

### 要求五：倫理與法律問題（五個子項）⭐

**為什麼重要**：確保產品符合倫理、以負責任方式運行、與組織價值觀一致 → **增強信任、保障長期成功與可持續發展**。

| 子項 | 要確保什麼 |
|---|---|
| **偏差**（Bias） | 不存在偏差或歧視。避免使用**有偏差的資料、特徵或演算法**；用**多樣且具代表性**的資料訓練。考慮是否可能**對某些群體造成不成比例的影響** |
| **透明度**（Transparency） | 具有**透明度與可解釋性** —— 利害關係人應能理解**模型如何運作、使用什麼資料、決策如何形成** |
| **隱私**（Privacy） | 尊重使用者的**隱私與保密性**；依**隱私法規與倫理準則**收集及使用資料；考慮是否收集**敏感或個人資訊** |
| **公平性**（Fairness） | 模型不會因**種族、性別、社會經濟地位**等特徵歧視某些群體；⭐ 考慮是否可能**延續或加劇現有的不平等** |
| **問責制**（Accountability） | 建立**明確的問責機制**；利害關係人應能就負面影響**要求責任方及開發人員承擔責任**；考慮是否可能產生**意外後果** |

## 3.3.1 第一階段：業務與資料理解 ⭐⭐（A2 最重要的一節）

> **這一階段為整個資料分析過程奠定基礎。**
> **完成後應形成**：定義明確的業務目標與要求 + 初步行動計畫。

### 業務理解的五個任務

#### 一、闡明 ML 產品的業務價值

- 以**簡潔、具體**的方式清晰闡明問題陳述
  - 範例：「**預測客戶流失**」「**偵測詐欺交易**」
- 明確**業務價值要求**，討論**價值主張與 ML 解決方案之間的一致性**

> ⭐ **原文的關鍵建議**：
> 「一種有效的方法是**定義一個非機器學習基準（non-ML baseline）**，
> 可以採用**當前的工作方式**作為基準，以便向業務利害關係人說明機器學習任務可能帶來的影響。」
>
> 🎯 **Bank X 直接對應**：**對照組的 9.94% 轉換率就是你的非 ML 基準**！
> 這不是我編的，是框架明確要求的東西，而資料剛好給了你。

#### 二、定義成功標準 ⭐（A2 必寫）

**依據 IEEE 的 SDLC 標準**：**要求的「可衡量性」是基本原則之一**。
每項成功標準必須**相互協調、與系統整體要求一致**，以避免產生**相互矛盾的目標**。

> **建議從兩個層面衡量成功。通常，一項業務成功標準會對應多項機器學習成功標準。**

| | **業務成功標準**（Business Success Criteria） | **機器學習成功標準**（ML Success Criteria） |
|---|---|---|
| 形式 | **KPI**（用於衡量 ML 應用相關性的**財務指標**） | 模型品質要求的**最低可接受效能水平** |
| 原文範例 | 製造業品質檢查：KPI = 「**自動化質量檢查為每個零部件節省的成本**」 | 若需優於當前人工檢查的 **3% 漏檢率** → 最低成功標準 = 「**準確率高於 97%**」 |

#### ⭐ 原文完整案例：零售銷售預測（照這個結構寫 A2）

**情境**：大型零售公司，有過去五年歷史銷售資料，特徵包括：**日期、門店位置、產品類別、銷量、價格、促銷活動**。
**現況**：持有價值 **$1,000,000** 的過剩庫存；因缺貨造成 **$500,000** 的銷售損失。
**業務目標**：將銷售預測準確率提高**至少 10%**。

**業務成功標準怎麼算**：

| 項目 | 現況 | 改善 10% 後 | 節省 |
|---|---|---|---|
| 過剩庫存 | $1,000,000 | $900,000 | **$100,000** |
| 缺貨損失 | $500,000 | $450,000 | **$50,000** |
| | | **合計** | **$150,000** |

→ **業務成功標準 = 節省 $150,000**

**機器學習成功標準**：KPI 是**預測準確率**，用 **MAPE（平均絕對百分比誤差）** 衡量，
目標是**將 MAPE 改善 10%**。

> 🎯 **這個案例的結構完全可以套到 Bank X**：
> 現況成本（A$62,905 / 每位成功客戶 A$27.35）→ 改善後 → 節省金額 = 業務成功標準；
> ML 成功標準 = ROC-AUC 或 Recall 的目標值。

#### 三、檢查可行性

> **在啟動專案前檢查技術可行性，是確保 ML 方法整體成功的最佳實踐** ——
> 可**降低因錯誤預期而導致專案過早失敗的風險**。

> 📌 **原文註記（重要）**：「當 ML 演算法**首次應用於某個特定領域**時，通常會透過**概念驗證（PoC）**
> 來證明可行性。**如果已經存在 PoC，則直接建立以部署為重點的軟體專案會更加高效。**」

**原文案例**：零售公司有數百萬條記錄，訓練需要大量算力與記憶體。
**潛在挑戰**：所需**硬體的成本與可用性** —— 可能需購買高效能設備或租用雲端資源，
**成本可能超過專案所能創造的業務價值**；使用高峰期硬體資源**可用性可能有限**，延誤進度。

#### 四、確保符合法律與合規要求

法律與合規約束通常還會加入**透明度、公平性、信任**等倫理與社會因素。
應清晰定義**可解釋性要求**與**倫理考量**。

**原文案例**：零售公司可能收集**購買記錄、瀏覽行為、人口統計資訊**。
**參考答案**：
- 確保以**合法方式收集**並取得客戶的**適當同意**
- 確保**不使用敏感資訊**（例如醫療或財務資料）
- 確保模型**不會對某些人口群體產生偏差**
- 可能需**諮詢法律專家**
- 技術措施：**資料匿名化（anonymisation）、加密（encryption）、存取控制**

#### 五、制定產品開發計畫（五個要素）

| 要素 | 內容 |
|---|---|
| **時間表與里程碑** | 詳細專案時間表，包括六個主要階段、重要里程碑、可交付成果、截止日期 |
| **風險管理** | 識別潛在風險與減輕／規避策略（資料品質、模型效能等） |
| **團隊結構與角色** | 組建團隊、明確角色與職責、建立溝通渠道與工作流程 |
| **預算與資源** | 人員、硬體、軟體及其他資源的分配 |
| **利害關係人參與** | 定期進度更新、演示、提供表達回饋的機會 |

> 計畫應**全面、清晰且能靈活調整**，並**定期審查與更新**。

### 資料理解

> **關鍵警語**：「機器學習專案或產品**可能需要延後，直到完成資料收集**。
> **如果無法收集到品質足夠高的資料，專案甚至可能需要終止。**」

**資料收集不是靜態任務，而是迭代任務**。
⭐ **應記錄對資料集所作的修改**，以降低產生**無法複現或錯誤結果**的風險。
**對資料實施版本控制**是確保可複現性與品質的重要工具 —— 有助於追蹤**錯誤與不利的資料修改**。

### 六、資料目錄、資料剖析、資料驗證（A2「資料理解」段落照這三項寫）

| | 定義與做法 |
|---|---|
| **資料目錄**<br>Data catalogue | **資料理解的基礎**。描述**資料資產及其屬性**並展開探查，以了解底層的**資料收集與處理過程**。<br>應在**元資料層面**定義，並**允許所有利害關係人存取** → 讓他們用領域知識補充**輸入訊號的格式、單位、描述** |
| **資料剖析**<br>Data profiling | 根據資料資產屬性的**統計特性**實施 —— **平均值、方差、最大值、最小值**等。<br>應使用**具充分技術依據的資料剖析與資料分布視覺化** |
| **資料驗證**<br>Data verification | 根據**資料品質要求**檢查生產資料的品質。**未達要求的資料應舍棄並儲存起來供人工分析**。<br>降低低品質資料導致效能下降的風險，也有助於**發現不斷變化的資料分布或不穩定的輸入** |

## 3.3.2 第二階段：資料工程

> **關鍵觀念**：「資料工程**並不是一個靜態階段**。如果後續階段（建模或部署）發現資料存在錯誤，
> 就需要**返回資料工程階段重新處理資料**。」← 這是 CRISP-ML 迭代性的具體體現。

**特徵工程的定義**：對模型的輸入進行**修改或預處理**，使模型（例如神經網路）能**更容易產生準確的結果**。

**頁面活動**：「資料工程涉及的步驟」互動元件。
**Kaggle 練習**：Comprehensive data exploration with Python。
**延伸**：Guyon & Elisseeff《變數與特徵選擇簡介》（Canvas PDF，特徵選擇方法的經典論文）。

## 3.3.3 第三階段：機器學習模型工程

> **輸入**：第一階段定義的**要求與限制** → 指導模型工程過程，建構一個或多個**符合既定限制與要求**的模型。
> **包含**：模型選擇、模型開發與訓練、模型註冊，以及**確保可複現性**的指導。

### 一、模型選擇

**選擇依據**：ML 目標與業務目標 · 資料 · ML 應用需滿足的**專案邊界條件**。

> ⭐ 原文再次點名：「**不存在一個能夠在所有問題類別中都取得最佳表現的模型，
> 這就是機器學習中的「沒有免費午餐」定理。**」

> ⭐ **最佳實踐**：「**從容量較低的模型開始，將其作為基準模型，再逐步提高模型容量。
> 在每個階段進行驗證，可以確認複雜度的提升是否帶來了實際益處，並避免模型出現不必要的複雜性。**」

### 二、模型訓練

**學習問題（learning problem）包含四個要素**：

| 要素 | 定義 |
|---|---|
| **目標函數**（objective） | 用於**評估模型效能的代理指標**；⭐ **必須根據業務成功標準對目標進行調整** |
| **優化器**（optimiser） | 定義**學習策略**，以及**如何調整模型參數**以改善目標函數的結果 |
| **正則化**（regularisation） | 可納入目標函數、優化器或模型本身；用於**降低過擬合風險**、幫助模型**泛化** |
| **交叉驗證**（cross-validation） | 用於**特徵選擇、優化超參數、檢驗對未見資料的泛化能力**；<br>以拆分歷史資料為基礎（訓練／驗證／測試），**測試資料作為目標環境的替代資料** |

#### 使用無標籤資料與預訓練模型

- 為資料加標籤**成本可能很高**，並可能限制資料集規模
- 可利用**無標籤資料**（例如**半監督學習演算法**）
- 可使用**遷移學習** —— 利用通用的預訓練模型，**用少量相關的有標籤資料微調**

#### 集成學習方法（Ensemble methods）

**做法**：訓練**多個模型**並**匯總各模型的決策**得出最終決策。模型可以是不同類型，也可以是同類型的多個實例。
**效益**：構建**容錯能力更強**的系統 —— **一個模型的錯誤可能由其他模型的結果補償**。
**成熟技術**：**提升法（Boosting）** 與 **裝袋法（Bagging）**。
⭐ **額外用途**：集成模型還可用於**計算不確定性估計**，並**突出模型置信度較低的區域**。

#### ⭐ 可複現性（Reproducibility）

> **為什麼難**：ML 訓練過程通常具有**非凸性（non-convex）與隨機性**，並採用**隨機化的資料拆分**方式。

**兩個不同層面**：

| 層面 | 內容 |
|---|---|
| **方法可複現性** | 根據詳盡說明重新構建模型；需共享**演算法、資料集、超參數、執行環境**。<br>執行環境資訊包括：**軟體版本、硬體、隨機種子**。<br>演算法應**詳細描述**（提供程式碼或偽代碼）+ 更高層級的設計資訊與假設 |
| **結果可複現性** | ⭐ **最佳實踐：使用不同的隨機種子驗證模型的「平均效能」，並評估效能的「方差」。**<br>⚠️ 「**只報告模型的最佳效能是一種常見但值得質疑的做法。**」<br>**較大的效能方差表明演算法較為敏感**，也會使人對模型的穩健性產生疑問 |

### 三、模型註冊（Model Registry）

**目的**：追蹤因先前模型修改而變化的**效能及其原因**，透過確定哪些修改是有益的來理解模型，提升整體品質。

**實用框架**：**Model Cards Toolkit**（模型卡）
**儲存方式**：可存為**檔案文件**，也可作為**模型元資料存入資料庫**，以便隨時**搜尋、分析、報告**。
**業界工具**：**MLFlow**（廣泛用於模型註冊）

## 3.3.4 第四階段：模型評估

> **又稱「離線測試」（offline testing）**。
> **目的**：確保模型滿足在**業務與資料理解階段定義的要求與 ML 成功標準**。

### ⭐ 七項評估特性（原文列出，A2 的評估表可以照抄）

> 「**建議至少從六項相互補充的特性對模型進行評估。**」

| # | 特性 |
|---|---|
| 1 | **效能指標**（performance metrics） |
| 2 | **穩健性**（robustness） |
| 3 | **公平性**（fairness） |
| 4 | **可擴展性**（scalability） |
| 5 | **可解釋性**（explainability） |
| 6 | **模型複雜度**（model complexity） |
| 7 | **模型資源需求**（resource demand） |

> ⭐ **原文的關鍵立場**：
> 「除效能指標外，還**必須評估穩健性、可解釋性和延遲等非量化指標（soft measures）**。」
> 「根據具體應用，可以為不同指標**賦予不同的權重**。
> **在實際應用中，可解釋性或穩健性的重要程度可能高於準確率。**」
> 「還可能需要評估模型的**公平性和隱私風險**，並採取相應的**風險緩解措施**。」
>
> 📌 這正是 A2 範例 Example_1 用**加權指標表**的依據 —— 那不是它自創，是框架要求的。

### ⭐ 案例研究：Zillow（房地產公司，2021 年虧損數億美元）

**發生什麼**：知名線上房地產公司 Zillow 在 **2021 年**因其**演算法與定價模型的問題**，
**虧損了數億美元**（iBuying 即時購房業務）。

**教訓（原文）**：
> 「這個案例深刻揭示了在**使用 AI 和 ML 演算法進行商業決策時，模型評估的重要性**。」
> 「**只依賴準確率指標可能會導致系統表現不理想和財務損失。**
> ML 模型還應接受**其他特性方面的測試，例如模型行為、可用性和公平性**。」

> 🎯 **A2 用法**：這是一個**具名、可查證、有金額**的真實失敗案例。
> 放在「模型評估」段落或「風險」段落，比空泛講「評估很重要」有力得多。

## 3.3.5 第五階段：模型部署

**定義**：將 ML 模型**整合到現有軟體系統**的過程。通過評估階段後即可部署到生產環境提供預測。

### 三種部署方式

| 方式 | 說明 |
|---|---|
| **REST API 提供線上預測** | 微服務形式 |
| **嵌入邊緣設備或行動設備** | Edge / mobile |
| **離線批量預測系統的一部分** | ⭐ **Bank X 就是這種**（夜間批次跑，隔天出名單） |

### 選擇合適的硬體

應根據**選定的部署方式**選擇推理硬體，並確保**與現有硬體相容**。
> 雲服務可提供**可擴展的計算資源**，但**嵌入式系統通常面臨嚴格的資源限制**。

**三種優化方式**：
- 根據目標硬體的 **CPU 和 GPU 可用性**優化
- 針對**目標作業系統**優化（已在 Android 和 iOS 上驗證）
- 針對**特定平台**優化 ML 工作負載

### ⭐ 部署策略（A2 可寫）

> **為什麼需要**：「即使模型在之前的各個階段都經過嚴格評估，
> **仍有可能存在整個過程中未被發現的錯誤**。因此，在全面推出之前，最佳實踐是制定適當的部署策略。」

| 類型 | 策略 | 說明 |
|---|---|---|
| **增量式／漸進式** | **金絲雀部署（canary deployment）** | 先讓小比例流量使用新模型 |
| **一次性切換** | **藍綠部署（blue-green deployment）** | 兩套環境整批切換 |

**頁面活動**：情境題 —— 「在以下情形中，你會選擇哪一種部署策略？」

### 使用者接受度與可用性

> 「即使模型已通過所有評估階段，其**使用者接受度和可用性仍可能未達預期**。
> 模型可能**難以理解**，或者**無法涵蓋邊緣情況**。」

**最佳實踐**：**構建原型，邀請最終使用者參與實地測試**。

**測試時應評估**：**使用者接受度、使用率、使用者體驗**。
**還應提供**：**使用者指南**與**免責聲明**，說明系統的**功能與局限**。

## 3.3.6 第六階段：模型監控與維護

### ⭐ 什麼是機器學習漂移（ML drift）

> **前提**：「隨著時間的推移，AI 模型的預測效能會下降，**這是不可避免的**。」

| 類型 | 定義 |
|---|---|
| **概念漂移**（concept drift） | **資料與預測目標之間的「關係」發生變化** |
| **資料漂移**（data drift） | **生產資料不再與歷史訓練資料相似** |

> ⚠️ 原文提醒：「**識別哪些機器學習漂移具有實際意義，哪些只是偽漂移或可接受的漂移，是一項繁瑣的工作。**」

### 效能下降的根本原因

> **主要原因是以下假設不再成立**：
> **「訓練資料與用於推理的輸入資料來自相同的資料分布。」**

- 資料分布隨時間變化 → **訓練集逐漸過時**，無法再準確反映當前分布的特徵
- 變化可能發生在**特徵、標籤或兩者**之中
- ⭐ **變化頻率取決於領域**：
  - **股票市場資料波動性很高**
  - **大象的視覺特徵在未來幾年內通常不會明顯變化**

> 🎯 **A3 直接對應**：A3 的後續問題就是問「銀行放寬資格標準後，新客群與舊客群不同，
> 原模型還能用嗎？」—— **那就是資料漂移**。答案要引用這一節。

### 一、持續評估模型

**監控什麼**：
- 比較**傳入資料與預測標籤的統計特性**與**訓練資料的統計特性**，監控**所有輸入訊號和特徵**
- 根據**輸入資料模式（schema）**驗證傳入資料是否正確；
  **不符合既定資料模式的輸入可視為異常，由模型拒絕處理**
- 若能獲得**傳入資料的真實標籤**（例如預測任務），可**直接監控並記錄模型效能**
- 監控階段還包括**將模型效能與預先定義的成功標準比較**

**⭐ 何時需要更新模型（三個觸發條件）**：
1. **輸入訊號發生顯著變化**
2. **異常數量達到特定閾值**
3. **模型效能下降到最低可接受水平**

> ⭐ **決策原則**：「在決定是否更新模型時，應**同時考慮更新模型的成本，
> 以及使用過時模型產生錯誤預測所造成的成本**。」

### 二、更新模型

- 收集**新資料**，根據已變化的資料分布**重新訓練**
- ⚠️ **新資料通常必須加標籤，而資料標註可能成本高昂**
- ⭐ **建議用新資料「微調」現有模型，而不是從零開始訓練全新模型**
- 為應對變化的資料分布，**可能還需重新執行部分建模步驟**
- **每次更新後的模型都必須重新接受評估**，確認符合要求才能部署
- ⭐ **應將更新後模型的效能與之前版本比較** —— 有助於了解**效能隨時間下降的速度**

## 3.4 機器學習運維（MLOps）簡介

> 🚨 **原文直接點名**：「**在評估任務二中，你需要提出用於機器學習開發與運維的 MLOps 設計方案。**」

### 核心命題

> 「資料科學家或許能夠…在**離線環境**中創建並訓練一個在**留出集**上具有良好預測效能的 ML 模型。

**MLOps 定義**：一種**機器學習工程「文化」和「實踐」**，旨在**整合 ML 系統開發（Dev）與 ML 系統運維（Ops）**。

**MLOps 帶來的效益**：加快模型交付速度、提高交付可靠性、**降低運營成本**、改善模型效能。

**成熟度的意義**：「這些步驟的**自動化程度**決定了機器學習流程的成熟度，
該成熟度體現了**利用新資料或新實施方案來訓練新模型的速度**。」

## 📚 MLOps 三個成熟度級別（以下取自 Canvas 所附 4 份 Google Cloud PDF 全文）

> 來源：Google Cloud Architecture Center《MLOps: Continuous delivery and automation pipelines
> in machine learning》，最後審閱 2024-08-28，CC BY 4.0。
> 作者：Jarek Kazmierczak（Solutions Architect）、Khalid Salama（Staff SWE, ML）、Valentín Huerta（AI Engineer）。
> **Canvas 頁面 3.4.1–3.4.3 只寫「讀這篇然後答題」，實質內容全在這些 PDF 裡。**
> 本地副本：[`../refs/unit3/`](../refs/unit3/)

### ⭐ 前置一：ML 系統只有一小部分是 ML 程式碼

> 「**只有一小部分的真實世界 ML 系統是由 ML 程式碼構成的。所需的周邊元素龐大而複雜。**」

**周邊系統組件（10 項）**：
配置 · 自動化 · **資料收集** · **資料驗證** · 測試與除錯 · 資源管理 ·
模型分析 · **流程與元資料管理** · 服務基礎設施 · **監控**

（改編自論文 *Hidden Technical Debt in Machine Learning Systems*）

### ⭐ 前置二：DevOps vs MLOps —— ML 系統的五個不同之處（高頻考點）

| 面向 | ML 系統與一般軟體系統的差異 |
|---|---|
| **團隊技能**<br>Team skills | 團隊通常包含**資料科學家或 ML 研究人員**，專注於探索性資料分析、模型開發與實驗；<br>**這些成員未必是能建構生產級服務的軟體工程師** |
| **開發**<br>Development | **ML 本質上是實驗性的** —— 要嘗試不同特徵、演算法、建模技術、參數配置。<br>挑戰在於**追蹤什麼有效、什麼無效**，並在**最大化程式碼重用性的同時維持可複現性** |
| **測試**<br>Testing | 比測試其他軟體系統**更複雜**。除了典型的單元測試與整合測試，還需要：<br>**資料驗證、訓練後模型品質評估、模型驗證** |
| **部署**<br>Deployment | **不只是把離線訓練好的模型部署成預測服務**。<br>ML 系統可能需要部署**多步驟 pipeline，以自動重新訓練並部署模型** |
| **生產**<br>Production | 模型效能下降**不只因為程式碼次優，還因為資料輪廓不斷演變**。<br>⭐「**模型衰退的方式比傳統軟體系統更多**」<br>→ 需要**追蹤資料的摘要統計**並**監控線上效能**，在數值偏離預期時**發送通知或回滾** |

### ⭐ 前置三：CI / CD / CT 在 ML 中的意義（必背）

| 縮寫 | 在一般軟體 | ⭐ 在 ML 系統 |
|---|---|---|
| **CI**<br>持續整合 | 測試與驗證**程式碼和組件** | 「**不再只是**測試驗證程式碼與組件，**還要測試驗證資料、資料 schema 和模型**」 |
| **CD**<br>持續交付 | 交付**單一軟體套件或服務** | 「**不再是**單一套件或服務，**而是一個系統（ML 訓練 pipeline），它應該自動部署另一個服務（模型預測服務）**」 |
| **CT**<br>**持續訓練** | — | ⭐ **「ML 系統獨有的新特性」**，關注**自動重新訓練並提供模型服務** |

### ⭐ 前置四：ML 的資料科學八步驟

> 「在定義業務用例並建立成功標準之後，將 ML 模型交付到生產環境的過程包含以下步驟。
> **這些步驟可以手動完成，也可以由自動 pipeline 完成。**」

| # | 步驟 | 內容 |
|---|---|---|
| 1 | **資料提取**（Data extraction） | 從各種資料來源**選擇並整合**相關資料 |
| 2 | **資料分析**（Data analysis） | **EDA 探索性資料分析** → 理解模型預期的**資料 schema 與特徵**；識別所需的**資料準備與特徵工程** |
| 3 | **資料準備**（Data preparation） | 資料清洗、**拆分為訓練／驗證／測試集**、套用資料轉換與特徵工程 |
| 4 | **模型訓練**（Model training） | 用準備好的資料實作不同演算法訓練多個模型；**超參數調校**取得最佳模型 |
| 5 | **模型評估**（Model evaluation） | 在**留出測試集**上評估品質，輸出一組**指標** |
| 6 | **模型驗證**（Model validation） | 確認模型**適合部署** —— **其預測效能優於某個基準** |
| 7 | **模型服務**（Model serving） | 部署到目標環境提供預測：**REST API 微服務** / **嵌入邊緣或行動設備** / **批量預測系統的一部分** |
| 8 | **模型監控**（Model monitoring） | 監控預測效能，**可能觸發 ML 流程的新一輪迭代** |

> 📌 **注意步驟 5 與 6 的區別**：**評估 = 產出指標；驗證 = 拿指標跟基準比、做部署決策。**
> 這兩個常被混為一談，是好考點。

## 3.4.1 成熟度級別 0：手動流程

> 「許多團隊擁有能夠構建先進模型的資料科學家和 ML 研究人員，
> 但其**構建和部署 ML 模型的流程完全依賴手動操作**。這被視為基礎成熟度級別。」

### 七項特徵

| # | 特徵 | 說明 |
|---|---|---|
| 1 | **手動、腳本驅動、互動式流程** | **每一步都是手動的** —— 資料分析、資料準備、模型訓練、驗證。<br>需要**手動執行每一步、手動從一步過渡到下一步**。<br>通常由資料科學家在 **notebook 中互動式撰寫與執行的實驗程式碼**驅動 |
| 2 | **ML 與運維脫節** | **建立模型的資料科學家**與**把模型部署成預測服務的工程師分離**。<br>資料科學家把訓練好的模型當成**產出物**交給工程團隊。<br>⚠️ 交接方式包括：放到儲存位置、簽入程式碼倉庫、上傳到模型註冊表。<br>⭐ **工程師需在生產環境提供低延遲服務所需的特徵，這可能導致「訓練—服務偏斜」（training-serving skew）** |
| 3 | **發布迭代不頻繁** | 假設團隊只管理**少數幾個不常變動的模型**。<br>⭐ **新模型版本一年只部署幾次** |
| 4 | **沒有 CI** | 因為假設實作變更很少，CI 被忽略。測試程式碼通常是 notebook 或腳本執行的一部分 |
| 5 | **沒有 CD** | 因為模型版本部署不頻繁，CD 不被考慮 |
| 6 | **部署指的是「預測服務」** | ⭐ **只關心把訓練好的模型部署成預測服務**（例如帶 REST API 的微服務），<br>**而不是部署整個 ML 系統** |
| 7 | **缺乏主動效能監控** | **不追蹤或記錄模型的預測與行為** —— 而這是偵測**效能下降與行為漂移**所必需的 |

> 📌 補充：工程團隊可能有自己複雜的 API 配置、測試與部署設定（安全、回歸、負載與金絲雀測試）。
> 新版本上線通常會先經過 **A/B 測試或線上實驗**，再全量服務。

### 挑戰與對策

> 「MLOps 級別 0 在**許多剛開始把 ML 應用到用例的企業中很常見**。
> 當模型很少變更或訓練時，這種手動、資料科學家驅動的流程**可能已經足夠**。
> **但實務上，模型在真實世界部署後經常失效** —— 模型無法適應環境動態的變化，
> 或描述環境的資料的變化。」

**三項對策**：

| # | 對策 | 說明 |
|---|---|---|
| 1 | **主動監控生產環境中的模型品質** | 讓你能偵測**效能下降與模型陳舊（model staleness）**；作為**新一輪實驗與（手動）重新訓練**的提示 |
| 2 | **頻繁重新訓練生產模型** | 捕捉**不斷演變與新出現的模式**。<br>範例：**推薦時尚商品的 app，其推薦應適應最新趨勢與商品** |
| 3 | **持續用新實作進行實驗** | 嘗試新的**特徵工程、模型架構、超參數**。<br>範例：**人臉偵測的臉部模式是固定的，但更好的新技術可以提升偵測準確率** |

> **結論**：要解決手動流程的挑戰，**CI/CD 與 CT 的 MLOps 實踐會有幫助** ——
> **部署 ML 訓練 pipeline 可啟用 CT**，並可建立 CI/CD 系統來快速測試、建構、部署 pipeline 的新實作。

## 3.4.2 成熟度級別 1：ML pipeline 自動化（持續訓練 CT）

> **目標**：「**透過自動化 ML pipeline 來執行模型的持續訓練**；
> 這讓你能達成**模型預測服務的持續交付**。」

**要達成需要引入**：**自動化的資料驗證與模型驗證步驟**，以及 **pipeline 觸發機制與元資料管理**。

### 六項特徵

| # | 特徵 | 說明 |
|---|---|---|
| 1 | **快速實驗**（Rapid experiment） | ML 實驗的各步驟被**編排（orchestrated）**，步驟間的轉換是**自動的** → 快速迭代、更容易把整條 pipeline 搬到生產 |
| 2 | **生產環境中的模型 CT** | 模型在生產環境中**依據即時 pipeline 觸發器、用新鮮資料自動訓練** |
| 3 | ⭐ **實驗—運維對稱性**<br>(Experimental-operational symmetry) | **開發／實驗環境使用的 pipeline 實作，同樣用於預生產與生產環境** ——<br>「這是 MLOps 實踐中**統一 DevOps 的關鍵面向**」 |
| 4 | **組件與 pipeline 的模組化程式碼** | 組件需**可重用、可組合、可跨 pipeline 共享**。<br>**EDA 程式碼仍可留在 notebook，但組件的原始碼必須模組化**。<br>⭐ **組件最好容器化**，以：① 把執行環境與自訂程式碼運行時**解耦** ② 讓程式碼在開發與生產環境間**可複現** ③ **隔離每個組件**（各自的運行環境版本、語言、函式庫） |
| 5 | **模型的持續交付** | 生產環境中的 pipeline **持續為新訓練的模型交付預測服務**；模型部署步驟是**自動的** |
| 6 | ⭐ **Pipeline 部署**<br>(Pipeline deployment) | **級別 0 部署的是「訓練好的模型」；級別 1 部署的是「整條訓練 pipeline」** ——<br>它會**自動且週期性地執行**，把訓練好的模型當成預測服務提供 |

> 📌 **級別 0 vs 級別 1 的一句話差別**：**部署模型 → 部署 pipeline。**

## 3.4.2.1 級別 1 的新增組件

### 一、資料驗證與模型驗證

#### 資料驗證（在模型訓練「之前」）

**目的**：決定**應該重新訓練模型，還是停止 pipeline 執行**。

| 偏斜類型 | 定義 | 應對 |
|---|---|---|
| **資料 schema 偏斜**<br>(Data schema skews) | **輸入資料的異常** —— 不符合預期 schema 的資料流入下游步驟。<br>包括：**收到非預期的特徵、沒收到所有預期的特徵、特徵值超出預期** | ⭐ **應停止 pipeline**，讓資料科學團隊調查；團隊可能發布修正或更新 pipeline 來處理 schema 變化 |
| **資料值偏斜**<br>(Data values skews) | **資料統計特性的顯著變化** —— 代表資料模式正在改變 | ⭐ **應觸發模型重新訓練**以捕捉這些變化 |

> 📌 **關鍵區分：schema 偏斜 → 停止；值偏斜 → 重訓。** 這是很好的考點。

#### 模型驗證（在成功訓練「之後」、晉升到生產「之前」）

**離線模型驗證包含四件事**：
1. 用訓練好的模型在**測試資料集**上產生**評估指標值**，評估預測品質
2. ⭐ **把新模型的指標與「當前模型」比較** —— 生產模型、基準模型或其他業務要求模型。
   **確保新模型效能優於當前模型才晉升到生產**
3. ⭐ **確保模型效能在資料的「各個區隔」上保持一致**。
   原文範例：「新訓練的**客戶流失模型**整體準確率可能優於前一版，
   **但各客戶地區的準確率可能有很大的方差**」
4. **測試模型的可部署性** —— **基礎設施相容性**、與**預測服務 API 的一致性**

> ⭐ **除了離線驗證，新部署的模型還要經過「線上模型驗證」** ——
> 在**金絲雀部署或 A/B 測試**設定中，才開始為線上流量提供預測。

### 二、特徵存儲庫（Feature Store）—— 級別 1 的「可選」組件

**定義**：一個**集中式儲存庫**，用於**標準化特徵的定義、儲存與存取**，供訓練與服務使用。
**需要提供的 API**：**高吞吐量的批次服務** + **低延遲的即時服務**，並同時支援訓練與服務工作負載。

**幫助資料科學家做四件事**：
1. **發現並重用**既有特徵集，而不是重新建立相同或相似的特徵
2. 透過維護特徵及其元資料，**避免出現定義不同的相似特徵**
3. 提供**最新的特徵值**
4. ⭐ **避免「訓練—服務偏斜」** —— 把特徵存儲庫當成實驗、持續訓練、線上服務的**單一資料來源**，
   確保**訓練用的特徵與服務時用的特徵是同一批**

| 用途 | 怎麼用特徵存儲庫 |
|---|---|
| **實驗** | 資料科學家取得**離線擷取**來跑實驗 |
| **持續訓練** | 自動訓練 pipeline **批次取得最新特徵值** |
| **線上預測** | 預測服務**批次取得該實體的相關特徵值**（例如客戶的年齡、購買歷史、瀏覽行為）——<br>**一次全部取得而非逐一取得**，管理多個實體時效率更高 |

### 三、元資料管理（Metadata Management）

**目的**：記錄**每次 pipeline 執行**的資訊，協助**資料與產出物的血緣（lineage）、可複現性、比較**，並**除錯錯誤與異常**。

**每次執行要記錄的 7 項元資料**：

| # | 記錄什麼 |
|---|---|
| 1 | 執行的 **pipeline 與組件版本** |
| 2 | **開始與結束的日期時間**，以及**每個步驟花了多久** |
| 3 | **pipeline 的執行者** |
| 4 | 傳給 pipeline 的**參數引數** |
| 5 | ⭐ **指向每一步產出物的指標** —— 準備好的資料位置、驗證異常、計算出的統計量、從類別特徵擷取的詞彙表。<br>**追蹤這些中間輸出，讓 pipeline 在某步失敗後能從最近的步驟續跑，不必重跑已完成的步驟** |
| 6 | **指向前一個訓練好的模型的指標** —— 需要**回滾**時用，或在模型驗證階段用新測試資料**產生前一版模型的評估指標**時用 |
| 7 | 模型評估階段產生的**訓練集與測試集的評估指標** —— 用來與前一版模型的紀錄比較 |

### ⭐ 四、ML pipeline 觸發器（五種，A2 可直接用）

| 觸發方式 | 說明 |
|---|---|
| **依需求**（On demand） | 臨時的**手動執行** |
| **依排程**（On a schedule） | 新的**已標註資料**以**每日／每週／每月**的頻率系統性地取得。<br>⭐ **重訓頻率取決於：資料模式變化的頻率 + 重訓的成本** |
| **當有新訓練資料時** | 資料**不是系統性提供**，而是**臨時**在收集到並放進來源資料庫時才有 |
| **當模型效能下降時** | 出現**明顯的效能下降**時重訓 |
| **當資料分布顯著改變時（概念漂移）** | ⭐「**很難評估線上模型的完整效能，但你注意到用於預測的特徵的資料分布有顯著變化。**<br>這些變化暗示模型已經**陳舊（gone stale）**，需要用新鮮資料重訓」 |

> 🎯 **Bank X 適用**：官方 Notebook 的設計是**每日用當天實際通話結果重訓** →
> 對應「**依排程（每日）**」+「**當模型效能下降時**」兩個觸發器。

### 級別 1 的挑戰（→ 為什麼要升到級別 2）

> 「假設 pipeline 的新實作**不常部署**、你只管理**少數幾條 pipeline**，
> 那你通常是**手動測試** pipeline 及其組件、**手動部署**新的 pipeline 實作，
> 並把測試過的原始碼**交給 IT 團隊**部署到目標環境。
>
> **這種設定適合「基於新資料部署新模型」，而不是「基於新的 ML 想法」。**
>
> 但你需要嘗試新的 ML 想法並快速部署 ML 組件的新實作。
> **如果你在生產環境管理很多條 ML pipeline，就需要 CI/CD 設定來自動化 pipeline 的建構、測試與部署。**」

## 3.4.3 成熟度級別 2：CI/CD pipeline 自動化

> **目的**：「為了**快速且可靠地更新生產環境中的 pipeline**，你需要一個**穩健的自動化 CI/CD 系統**。」
> **效果**：讓資料科學家能**快速探索特徵工程、模型架構、超參數的新想法**，
> 並**自動建構、測試、部署新的 pipeline 組件**到目標環境。

### 七個組件

原始碼控制 · 測試與建構服務 · 部署服務 · **模型註冊表** · **特徵存儲庫** · **ML 元資料存儲** · **ML pipeline 編排器**

### ⭐ CI/CD 自動化 ML pipeline 的六個階段

| # | 階段 | 輸出 |
|---|---|---|
| 1 | **開發與實驗** —— 迭代嘗試新的 ML 演算法與新建模，實驗步驟被編排 | **ML pipeline 各步驟的原始碼**，推送到原始碼倉庫 |
| 2 | **Pipeline 持續整合** —— 建構原始碼並執行各種測試 | **pipeline 組件**（套件、可執行檔、產出物），供後續階段部署 |
| 3 | **Pipeline 持續交付** —— 把 CI 階段的產出物部署到目標環境 | **已部署的 pipeline**，包含模型的新實作 |
| 4 | **自動觸發** —— pipeline 依排程或回應觸發器在生產環境自動執行 | **訓練好的模型**，推送到**模型註冊表** |
| 5 | **模型持續交付** —— 把訓練好的模型當成預測服務提供 | **已部署的模型預測服務** |
| 6 | **監控** —— 依據即時資料收集模型效能的統計資料 | **觸發器** —— 執行 pipeline 或啟動新的實驗週期 |

> ⚠️ **原文特別註明（重要，容易誤以為全自動）**：
> 「**資料分析步驟對資料科學家而言「仍然是手動流程」**，在 pipeline 開始新一輪實驗之前。
> **模型分析步驟「也是手動流程」。**」

### 持續整合（CI）階段的六類測試

當新程式碼提交或推送到原始碼倉庫時，pipeline 及其組件會被建構、測試、打包。除了建構套件、容器映像、可執行檔，CI 流程可包含：

| # | 測試 |
|---|---|
| 1 | **單元測試你的特徵工程邏輯** |
| 2 | **單元測試模型中實作的各種方法**。<br>原文範例：「你有一個函式接受一個**類別型資料欄位**，並把它編碼成 **one-hot 特徵**」 |
| 3 | ⭐ **測試模型訓練是否收斂** —— 即「**損失隨迭代下降**，並且**能對少數樣本記錄過擬合**」 |
| 4 | ⭐ **測試模型訓練不會產生 NaN** —— 因**除以零**或**處理極小／極大值**造成 |
| 5 | **測試 pipeline 中每個組件都產生預期的產出物** |
| 6 | **測試 pipeline 組件之間的整合** |

### 持續交付（CD）階段要考慮的八件事

| # | 考量 |
|---|---|
| 1 | **部署前驗證模型與目標基礎設施的相容性** —— 模型所需套件是否已安裝在服務環境；**記憶體、運算、加速器資源**是否可用 |
| 2 | ⭐ **測試預測服務** —— 用預期輸入呼叫服務 API，確認回應符合預期。<br>「這個測試通常能抓到**更新模型版本後、它預期不同輸入**時可能發生的問題」 |
| 3 | **測試預測服務的效能** —— **負載測試**以取得 **QPS（每秒查詢數）** 與**模型延遲**等指標 |
| 4 | **驗證資料** —— 用於重訓或批次預測 |
| 5 | **驗證模型在部署前達到預測效能目標** |
| 6 | **自動部署到測試環境** —— 例如由**推送程式碼到開發分支**觸發 |
| 7 | **半自動部署到預生產環境** —— 例如由**審查者核准後合併到主分支**觸發 |
| 8 | ⭐ **手動部署到生產環境** —— 在預生產環境**多次成功執行 pipeline 之後** |

### ⭐ 原文的總結（很適合當 A2 MLOps 段落的收尾）

> 「總結來說，**在生產環境實施 ML 不只意味著把模型部署成預測用的 API。
> 它意味著部署一條「能自動重新訓練並部署新模型」的 ML pipeline。**
> 建立 CI/CD 系統讓你能自動測試與部署新的 pipeline 實作，
> 讓你能**應付資料與business環境的快速變化**。
>
> ⭐ **你不必立刻把所有流程從一個級別搬到另一個級別。
> 你可以「逐步」實施這些實踐，來改善 ML 系統開發與生產的自動化程度。**」

> 🎯 **A2 用法**：這最後一句是選擇「較低成熟度級別」的**官方背書** ——
> 範例 Example_2 選 Level 0 並說明升級觸發條件，就是踩在這句話上。

## 📌 單元三測驗準備重點（自行歸納，非 Canvas 原文）

### 產品要求
1. **五大要求**：商業價值 / 技術可行性 / 資料品質 / 模型效能 / 倫理與法律。**每一項的子項要記**。
2. **技術可行性五子項**：相容性、可擴展性、安全性、整合、維護與支援。
3. **資料品質五子項**：相關性、完整性、準確性、一致性、**偏差**。
4. **模型效能四子項**：準確率、泛化能力、**穩健性（非功能特性，用「有噪聲時能否保持正確」衡量）**、延遲。
5. **倫理五子項**：偏差、透明度、隱私、公平性、**問責制**。
6. ⭐ **「效率有時比準確率更重要」**、**「可解釋性或穩健性的重要程度可能高於準確率」** —— 兩句原文立場。

### CRISP-ML 六階段
7. ⭐ **非 ML 基準（non-ML baseline）= 當前的工作方式**，用來說明 ML 的影響。
8. ⭐ **業務成功標準（KPI，財務指標）vs ML 成功標準（最低可接受效能）**；**一項業務標準對應多項 ML 標準**。
9. **零售案例的算法**：$100,000 + $50,000 = **業務成功標準 $150,000**；ML 標準 = **MAPE 改善 10%**。
10. **可行性檢查**：**PoC 用於首次應用到新領域；已有 PoC 就直接做部署導向的專案**。
11. **資料理解三件事**：**資料目錄（元資料層面）、資料剖析（統計特性）、資料驗證（不合格就舍棄並存起來人工分析）**。
12. **資料工程不是靜態階段** —— 後續發現錯誤要回頭重做。
13. **學習問題四要素**：目標函數、優化器、正則化、交叉驗證。
14. ⭐ **可複現性兩層面**：方法可複現（共享演算法/資料/超參數/環境含**隨機種子**）vs 結果可複現（**用不同隨機種子看平均效能與方差**；**只報最佳效能是值得質疑的做法**）。
15. **模型註冊**：Model Cards Toolkit、**MLFlow**。
16. **模型評估 = 離線測試**；**至少六項互補特性**；**Zillow 2021 年虧損數億美元**的案例。
17. **三種部署方式**；**金絲雀（漸進）vs 藍綠（一次性切換）**。
18. ⭐ **概念漂移（關係變）vs 資料漂移（資料不像訓練資料了）**。
19. **效能下降的根本原因**：「訓練資料與推理輸入來自相同分布」的假設不成立。
20. **更新模型的三個觸發**：輸入訊號顯著變化 / 異常達閾值 / 效能降到最低可接受水平。
21. ⭐ **決策原則**：比較「更新成本」vs「用過時模型的錯誤成本」。
22. **微調現有模型 > 從零訓練**。

### MLOps
23. ⭐ **MLOps 是 CRISP-ML 生命週期的「自動化框架」**。
24. ⭐ **DevOps vs MLOps 的五個差異**：團隊技能、開發（實驗性）、測試（多了資料驗證/模型驗證）、部署（多步驟 pipeline）、生產（**模型衰退方式比傳統軟體更多**）。
25. ⭐ **CI/CD/CT 在 ML 中的重新定義**；**CT 是 ML 獨有的新特性**。
26. **資料科學八步驟**；⭐ **模型評估（產出指標）vs 模型驗證（比基準、做部署決策）**。
27. **級別 0 的七項特徵**；⭐ **訓練—服務偏斜（training-serving skew）**；**一年只部署幾次**。
28. **級別 0 的三項對策**：主動監控 / 頻繁重訓 / 持續用新實作實驗。
29. ⭐ **級別 0 vs 1 的一句話**：**部署模型 → 部署 pipeline**。
30. **級別 1 六特徵**；⭐ **實驗—運維對稱性**；**組件要容器化的三個理由**。
31. ⭐ **資料驗證：schema 偏斜 → 停止 pipeline；值偏斜 → 觸發重訓**。
32. **模型驗證四件事**；⭐ **要檢查「各資料區隔」上效能是否一致**（客戶流失模型分地區的例子）。
33. **特徵存儲庫的核心價值 = 避免訓練—服務偏斜**。
34. **元資料管理 7 項**；⭐ **記錄中間產出物讓 pipeline 能從失敗處續跑**。
35. ⭐ **五種 pipeline 觸發器**。
36. **級別 2 的七個組件、六個階段**；⭐ **資料分析與模型分析「仍是手動」**。
37. **CI 的六類測試**；⭐ **測試訓練會收斂**（損失下降 + 能對少數樣本過擬合）、**測試不產生 NaN**。
38. **CD 的部署梯度**：**自動→測試環境；半自動→預生產；手動→生產**。
39. ⭐ **「不必立刻從一個級別搬到另一個級別，可以逐步實施」** —— 選低成熟度的官方背書。
