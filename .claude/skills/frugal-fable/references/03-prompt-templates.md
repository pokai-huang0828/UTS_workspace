# 03 · 派工 prompt 模板(六型,填空即用)

> 用法:複製對應模板 → 填 `<>` 欄位 → 照 [01](01-model-dispatch.md) §2 選 model 派出。
> 每份模板已內建:目標與動機 / 驗收條件 / 回報格式(三件套)。**別刪驗收段落**。
> v2,2026-07-09:新增 §摘要(本 repo 最常見派工型);既有五型**均有微調**(全部加「第一行 TL;DR」回報要求;§審查另調 model 建議與 verdict 格式)。微調清單見 CLAUDE.md 遷移紀錄,**待 Kenny 追認**;v1 備份 `.claude/backups/governance-2026-07-09/`。

## §搜尋(Explore · haiku)

```text
READ-ONLY 搜索。目標:<找什麼>。動機:<主任務為什麼需要它,讓你能自行判斷邊界案例>。
範圍:<目錄/檔型/排除項>。搜索廣度:<medium|very thorough>。
驗收條件:
1. 回報每個命中 = 路徑 + 行號 + ≤1 行摘錄(verbatim)。
2. 明確說「掃過哪些目錄、用過哪些關鍵字」— 沒找到也要報告掃描範圍,不准只回「找不到」。
3. 上限 <N> 條;超過就回總數 + 前 <N> 條 + 分佈說明。
回報格式:第一行一句話 TL;DR,之後編號清單,不要散文。不要修任何檔案。
```

## §摘要(Explore 或 general-purpose · haiku;要取捨判斷時 sonnet)

```text
READ-ONLY 消化任務。目標:把 <檔案/線程/目錄> 消化成主迴圈可直接使用的摘要。
動機:<主任務是什麼,摘要會被拿去做什麼決定>。
輸入:<路徑清單>。注意:handoff.md / changelog.md 這類 append-only 長檔,只讀最後 <N> 個 entry(除非任務明說要全檔)。
驗收條件:
1. 結構化輸出,欄位 = <例:日期|事件|影響|待決>,每條附 檔案:行號。
2. 對賬:來源共 <N> 個單元(entry/票/信),輸出涵蓋 N 個,或列出略過的是哪幾個+原因。
3. 關鍵數字/日期/ID/人名逐字抄,不改寫、不四捨五入。
回報格式:第一行一句話 TL;DR;主回報 ≤<40> 行;超出部分寫到 <scratchpad 路徑> 回傳路徑。不要修任何檔案。
```

## §實作(general-purpose · sonnet;高風險改 opus)

```text
實作任務。目標:<做出什麼>。動機:<給誰用、解什麼問題>。
輸入:<來源檔案路徑/資料;來源即規格,不要自行腦補內容>。
輸出:寫到 <確切路徑>(新檔;若要改既有檔,先 Read 再 Edit,禁整檔盲寫)。
硬規則:<例:逐字保真不改寫/數字不得失真/list 前空行/不碰 X 目錄>。
驗收條件:
1. <可檢查條件 1,例:17 題一題不少,編號 Q1–Q17 無跳號>
2. <可檢查條件 2,例:所有數字與來源逐字一致>
3. 自檢:交付前 read-back 你寫的檔,確認非空、結構完整。
回報格式:第一行一句話 TL;DR;檔案路徑 + 一行統計(<例:題數/行數>)+ 你注意到的異常 ≤3 條。不要回貼檔案全文。
```

## §重構(general-purpose · sonnet;會動多檔先做 1 檔試點)

```text
重構任務。目標:<把 X 改成 Y>。動機:<為什麼值得動>。
範圍:<明確檔案清單或 glob;清單外的一律不碰>。
不變式(改完必須仍成立):
1. <例:python .claude/scripts/build.py --check 必 exit 0>
2. <例:對外行為/輸出 byte-identical,只有內部結構變>
步驟:先改 <1 個代表檔> 回報 diff 摘要,等我說「繼續」才批次;批次時逐檔套同一 pattern。
驗收條件:每檔改動 ≤<N> 行、不變式全過、git status 只含範圍內檔案。
回報格式:第一行一句話 TL;DR;檔案清單 + 每檔一行「改了什麼」+ 不變式驗證輸出(命令+exit code)。
```

## §研究(general-purpose · sonnet 起步)

```text
研究任務。問題:<一句話問題>。動機:<答案會拿去做什麼決定>。
來源優先序:<例:repo 內檔案 > 官方文件 > 一般網頁;內部事實以 <SSOT 檔> 為準>。
驗收條件:
1. 每個結論附來源(檔案:行號 或 URL);查無來源的想法標「推測」。
2. 對「查不到」誠實回報查過哪裡,不准編造。
3. 若兩來源矛盾:並列兩說 + 各自出處,不要自行擇一。
回報格式:第一行一句話 TL;DR;結論(≤5 條)→ 證據表(結論|來源|信心 高/中/低)→ 建議下一步 ≤2 條。
長篇筆記寫到 <scratchpad 路徑>,主回報 ≤40 行。
```

## §審查(fresh Agent · sonnet;判斷級受審物用 opus;或 Codex read-only)

```text
對抗式審查。你是獨立驗收者,價值在於抓出產出者看不到的問題;預設立場 = 懷疑。
受審物:<檔案清單>。原始需求:<驗收條件原文,逐條照抄>。
檢查維度(逐項回答,不准跳過):
1. 逐條驗收條件:PASS/FAIL + 證據(檔案:行號)。
2. 規則互相打架:受審檔之間、受審檔與 <CLAUDE.md / 01–04 檔> 之間有無矛盾指令。
3. 路徑/命令實在性:文中每個路徑用 ls 驗、每個宣稱可跑的命令抽 <N> 條實跑(read-only 的才跑)。
4. 弱模型誤讀風險:哪句話 Sonnet/Haiku 會理解成別的意思?引用原句 + 說明會誤讀成什麼。
限制:READ-ONLY,不修檔;修復建議寫成清單交回。
回報格式:第一行 verdict(PASS / FAIL+問題數)→ 問題按嚴重度排序,each = 檔案:行號 + 原句 + 為什麼錯 + 建議改法。
```

## 通用尾註(每份派工都加)

```text
你的最終回覆是給指揮官的資料,不是給人類的信 — 不要客套、不要重複任務描述。
遇到超出範圍的問題:記下來放「異常」段,不要自行擴大範圍處理。
```
