# 09 ｜題目初評:公交服務可靠性預警系統(2026-11-04)

> **來源**:隊友在微信群提的題目(業務問題原文:「哪些線路和時段容易延誤?能不能提前 15–30 分鐘預警,讓調度員加派車輛、發布乘客通知」)＋即時資料核對〔[raw/realtime_sources_2026-11-04.md](raw/realtime_sources_2026-11-04.md)〕。
> **(推論)** = 我的判斷,不是課程或資料來源寫的。

## 1. 一句話

用香港巴士的即時到站資料,找出哪些路線、哪些時段最容易「等很久」或「串車」,提前 15–30 分鐘提醒調度員加車,並用 AI 寫好給乘客的通知。

## 2. 為什麼是好題目

- **業務問題具體**,剛好接得出 AT2 要的「業務目標 → 分析目標 → 任務」三層〔03 §3〕。
- **天生有即時展示**:AT3 要的資料介面＋分析介面＋互動介面,做成一張即時預警看板;「系統運行流暢」12 分最好拿〔Canvas AT3 評分標準〕(推論)。
- **分工順**:開發負責定時抓資料、資料庫、看板;Kenny 負責延誤規律分析和預測模型;業務/利害關係人負責調度員和乘客的需求、通知怎麼寫;項目負責排時程(推論)。
- **AI 用得自然**:模型預測風險,大語言模型把預警寫成「給調度員的處理建議」和「給乘客的通知草稿」,人確認後才發(推論)。
- **資料條款最清楚**:DATA.GOV.HK 可商業與非商業免費使用,註明來源即可〔raw/realtime〕。

## 3. 最關鍵的設計:「延誤」怎麼算

- 接口只有**預計**到站時間,**沒有實際到站紀錄**,也沒有逐班延誤欄位〔raw/realtime〕。
- 做法(推論,業界常用的「班距可靠度」):
  1. 每分鐘抓選定車站的預計到站時間(`stop-eta` 一次回傳該站所有路線)。
  2. 某班車的預計時間到了、下一輪消失 → 推定「這班車到站了」,記下推定的到站時間。
  3. 同一站同一路線,相鄰兩班的推定到站時間相減 = **實際班距**。
  4. 和官方時刻表(GTFS `frequencies.txt`)的**規定班距**比:實際班距超過規定的 1.5 倍 = 長時間等車;小於 0.3 倍 = 串車(門檻之後依資料再調)。
- 要先確認:GTFS 有沒有涵蓋九巴路線、是班距制還是逐班時刻〔raw/realtime ⚠️〕。

## 4. 香港 vs 新加坡

| | 香港(推薦) | 新加坡 |
|---|---|---|
| 金鑰 | 不用,現在就能抓 | 要申請 AccountKey |
| 更新 | 約 1 分鐘 | 20 秒 |
| 額外資訊 | 官方時刻表(規定班距)、天文台天氣 | 車廂擁擠度、是否依定位推算、規定班次頻率、每月各站上下車人數 |
| 條款 | 可商用,註明來源 | 可商用,醒目註明來源 |
| 隊友熟悉度 | 中文環境,比較熟(推論) | 英文環境 |

- 選香港的理由:**今天就能開始抓**,不用等申請;條款清楚;有規定班距可以比。
- 新加坡的優點(擁擠度、上下車人數)可以當報告裡的「延伸方向」。

## 5. 風險與對策

| 風險 | 對策 |
|---|---|
| 歷史資料要自己累積 | **最晚 11/10 開始**定時抓;到 12/6 寫 AT2 時約有 4 週資料(推論) |
| 抓資料的電腦要 24 小時開著 | 用一台雲端小主機或隊友的伺服器;資料每天備份 |
| 接口可能改版或中斷 | 記錄每次抓取成功率;展示時準備錄好的備用資料 |
| 「提前 15–30 分鐘」準度未知 | 成功標準先寫保守,累積資料後再調;一定要和「歷史同時段平均」基準比 |
| 範圍太大 | 只挑 5–10 條路線、30–50 個重點車站(推論) |
| 大陸隊友連不連得上 data.gov.hk | 沒測,開會時請北京的隊友試開一次接口網址 |

## 6. 1.12 目標設定草稿

**繁體(給 Kenny 看)**

- **項目目標(aim)**:幫香港巴士公司的調度中心提前發現可能出現的長時間等車或串車,讓調度員能提前 15–30 分鐘加派車輛或發布乘客通知,改善乘客的候車體驗。
- **具體目標(objectives)**:
  1. 從 11 月起,每分鐘收集 5–10 條選定路線的即時到站資料,連同官方規定班距(GTFS)和天氣資料,建立至少 4 週的歷史資料集。
  2. 定義並計算服務可靠度指標(實際班距比規定班距多等的時間、串車比例),找出最容易出問題的路線和時段。
  3. 建立預測模型,提前 15–30 分鐘預警長間隔或串車,並和「歷史同時段平均」基準比較(初步目標:召回率 ≥ 70%、精確率 ≥ 60%,資料累積後再調整)。
  4. 用大語言模型把預警寫成給調度員的處理建議和給乘客的通知草稿,由人確認後才發出。
  5. 2027 年 2 月前完成可以即時運作的預警看板原型,並請隊友扮演調度員做使用測試。
