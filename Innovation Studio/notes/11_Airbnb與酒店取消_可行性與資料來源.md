# 421048：Airbnb 與酒店訂單取消預測——可行性與資料來源

> 研究日期：2026-11-07。用途：第 5 組選題與 AT2 設計依據，並非已完成的系統或正式交件報告。
> 範圍假設：將 Airbnb 與「酒店訂單取消預測」視為兩個候選方向；另回答能否直接做 Airbnb 取消預測。
> 資料來源實查紀錄：[`Airbnb`](raw/airbnb_sources_2026-11-07.md)、[`酒店`](raw/hotel_sources_2026-11-07.md)。既有酒店實驗：[`T1`](08_深度分析/T1_酒店訂單取消.md)。

## 先給選題結論

**優先選酒店訂單取消風險與人工跟進原型。若全組更喜歡 Airbnb，改做房源價格定位與同類比較。僅依本次找到的公開資料，不選 Airbnb 訂單取消預測。**

| 要回答的問題 | Airbnb 公開房源資料 | 酒店訂單資料 |
|---|---|---|
| 一列代表什麼？ | 一個房源快照；日曆另為房源×日期；評論另為一則評論 | 一筆已完成結果追蹤的預訂紀錄 |
| 能直接學什麼？ | 房源標示價格、房型與地區差異；評論文字主題 | `is_canceled` 取消／未入住風險 |
| 最缺什麼？ | 真實逐筆訂單、取消時間與結果、成交價格 | 每個欄位在預測當下的歷史版本、干預及最終收益 |
| 適合本組的最小題目 | 同區同類房源的價格定位助手 | 取消風險排序＋人工跟進助手 |
| 可行性判斷 | 改題後可行；價格資料須先過品質檢查 | 歷史分析原型可行；上線有效性仍須另驗 |
| 最大誤用 | 把不可訂日期當已訂、估計收益當真實收益 | 使用結果後才知道的特徵，或把預測等同挽留成功 |

這是依目標標籤、資料時間語義與本組能力做的判斷，沒有用主觀分數冒充成功機率。Airbnb 的房源 ID 與酒店預訂紀錄沒有共同鍵，也不是同一市場；兩者不可拼接成一個訓練集。

## 1. 為什麼這兩題能對到作業

- AT2 的高分描述也要求說明前沿 AI 方法、選擇標準與前沿基準；應在計畫中交代為何選此模型／LLM，以及如何用品質、成本與延遲比較候選方法，不能到 AT3 才補 AI。
- AT3 分析報告的系統、分析結果與技術創新占 50/100；業務影響、部署計畫與建議占 30/100。
- AT3 的高分描述提到將前沿 AI 整合到可行動功能，並用互動介面與非技術使用者溝通。因此只交一個模型或一組圖，難以完整回應這些要求；加一個沒有評估的聊天機器人也不足以證明價值。

## 2. Airbnb：題目可以做，但必須換成資料答得出的問題

### 2.1 最小業務問題

**建議題名：雪梨 Airbnb 房源價格定位與市場比較助手。**

使用者：小型房東或物業管理者。問題：不知道自己的標價與同區、同房型、相近容納人數的房源差多少。系統提供可比房源、價格分布、差異解釋與待確認事項，支援人工定價討論。

可以回答「我的標價在可比房源裡偏高還是偏低？」；不能依此宣稱「這就是能最大化收益的價格」。公開標價不是成交價，也沒有需求對價格變化的反應，無法單靠回歸證明最佳定價。

### 2.2 資料來源與可用範圍

主要入口：[Inside Airbnb Get the Data](https://insideairbnb.com/get-the-data/)。它是獨立資料計畫，並非 Airbnb 公司提供的內部交易資料。資料假設須一起閱讀：[Data Assumptions](https://insideairbnb.com/data-assumptions/)。

| 檔案／資料 | 合理用途 | 不應推論 |
|---|---|---|
| `listings.csv.gz` | 房型、地區、容納人數、標價、評分與房東特徵 | 價格必然能成交、房東真實收入 |
| `calendar.csv.gz` | 可預訂狀態與最短／最長住宿限制 | 不可訂一定是已入住、狀態變化一定是取消 |
| `reviews.csv.gz` | 評論主題、語言、客人提到的優缺點 | 沒有評論就沒有入住；評論代表所有客人 |
| 地區邊界 | 地區聚合與地圖顯示 | 以近似座標辨識真實地址 |

本次下載入口的雪梨目錄日期為 **2026-09-16**，實檔 `last_scraped` 為 **2026-09-17**。全量 listings 有 **20,833 列×90 欄**、房源 ID 全唯一；`price` 缺 **3,112 列（14.94%）**，`bathrooms` 整欄空白。這批 calendar 表頭沒有價格欄；reviews 沒有逐則星等。日曆與評論僅檢查表頭，沒有全量品質結論。

新增的 `price_quote_checkin_date`／`checkout_date` 顯示報價入住日期與晚數不一致；`price` 與 `price_quote_price_per_night` 的關係尚未完整釐清。**在確認價格語義、限定可比入住條件之前，不承諾可比價格模型。** `estimated_occupancy_l365d` 與 `estimated_revenue_l365d` 是估計欄，不是實際訂單或收益；目前官方舊字典也不足以完整解釋新欄位。

下載入口標示 CC BY 4.0；站方 Data Policies 另有不要重發布整份資料的社群請求。本專案保留來源、下載說明、彙總與程式，原始房東／評論者資料不進 repo。詳見 [Data Policies](https://insideairbnb.com/data-policies/) 與來源紀錄。

### 2.3 先做品質檢查，再決定要不要上模型

1. 固定一個城市、一批快照，記錄目錄日期、`last_scraped`、下載時間及檔案雜湊；不同日期不是同時點市場。
2. 清理標價的貨幣符號與千分位，確認同一城市的貨幣口徑、價格欄意義與報價住宿條件；空值不能補成零。標價不代表含清潔費、服務費的最終總價。
3. 預先定義研究範圍，例如整套房、合理容納人數、短住可訂房源；公開所有排除條件和剩餘筆數。此範圍是團隊設計，不是官方分類。
4. 先檢查價格缺值是否集中在特定房型或地區，避免只剩部分房東卻稱為全市場。
5. 只用已驗證有值的房源特徵。新批次欄位可能整欄空；不能照別人的 notebook 預設浴室等欄一定可用。
6. 地圖只顯示區域或聚合，介面不展示房東姓名、個人頁面、評論者識別碼及可辨識的評論原句。

### 2.4 分析與模型設計

先確認價格欄語義及入住日期／晚數可比，再比較「同地區×房型×容納人數」價格中位數與分布。樣本不足就擴大比較範圍並提示，不能硬報精確行情。若無法建立價格可比性，降為房源供給與可訂狀態分析；此時要重新確認全組是否仍願意選題。

若品質足夠，再比較一個簡單回歸與一個樹模型；目標是預測**標示價格**。主要指標用 MAE，並按房型、價格帶與地區報誤差。長尾價格可用對數尺度輔助，但要回到實際貨幣單位解讀。

選定一個價格目標後，排除同列其他價格欄、原始報價內容及由價格推導的收益欄，避免模型從另一欄直接讀答案。

單快照的測試只能支持同批市場內的插值。若收集多期資料，同房源不得跨訓練與測試而被當成新房源泛化；要另外保留較晚快照測未來表現，並比較兩期都存在與新上架房源，揭露存活偏差。

若多快照欄位不一致或資料取得不穩，保留單期價格定位即可，不擴成動態定價。評論主題只作額外解釋；不在首版同時做情緒分類、旅遊推薦與取消預測。

### 2.5 展示與可交付成果

- 輸入房型、地區、容納人數與自己的標價。
- 顯示符合條件的可比房源數、價格區間與位置；房源太少時拒絕給強結論。
- 顯示模型估計標價與誤差說明；「高於可比中位數」不等於「應降價」。
- AI 依傳入的彙總數據產生一段價格定位說明，不宣稱查過未提供的即時市場。

**取消預測的停止條件：**若沒有逐筆預訂及取消結果，這個方向就不成立。日曆前後變化、評價消失、估計入住率均不能補成真實取消標籤。只有取得具授權的房東／管理公司交易與事件資料，重新確認樣本量、欄位時間與可用條件後，才重開取消題目。

## 3. 酒店取消：資料最貼題，但必須縮小成誠實的原型

### 3.1 最小業務問題

**建議題名：酒店預訂取消風險與人工跟進決策助手。**

使用者：預訂主管或收益管理人員。每天能聯絡的訂單有限，需要先找出值得確認的預訂。系統產生風險排序、相關特徵與人工確認草稿，主管核准後自行處理。

本資料能支持「歷史訂單風險排序的離線評估」。尚不能證明在新酒店、現在的市場、訂房當下或入住前某一天同樣有效，更不能證明打電話能降低取消。

### 3.2 來源層級

首要來源是 Antonio、de Almeida 與 Nunes 的 [Hotel booking demand datasets 論文](https://doi.org/10.1016/j.dib.2018.11.126)，原檔可由 [Europe PMC 論文補充資料](https://www.ebi.ac.uk/europepmc/webservices/rest/PMC6297060/supplementaryFiles) 取得，內含 `H1.csv` 與 `H2.csv`，本次已實際下載。開發可用 [TidyTuesday 合併 CSV](https://raw.githubusercontent.com/rfordatascience/tidytuesday/main/data/2020/2020-02-11/hotels.csv)，本次與兩個原始檔對照，統一字串空白與數值格式後，除新增 `hotel` 外的 31 欄逐格差異為零。Kaggle 便於取得，但不能代替原始論文的欄位定義、授權及抽取方法。

原論文標示 CC BY 4.0，資料作為論文附件提供，未見附件另列不同條款；引用作者、DOI、資料版本與修改方式。作者較新的 [2014–2023 酒店資料](https://zenodo.org/records/18119072) 有受限存取標示，本次未申請，不能拿來承諾更新資料已到手。

資料來自兩家葡萄牙酒店，不是 Airbnb、全球酒店或現代中國酒店市場。即使欄位與商業問題相似，也須清楚說明案例移轉限制。

### 3.3 已有證據能支持什麼

既有 T1 的資料規模為 119,390 列、合併後 32 欄，`is_canceled=1` 共 44,224 列，約 37.04%。兩個原始檔各有 31 欄，合併版另加 `hotel` 識別來源，欄數差異不是資料錯誤。

取消標籤包含未入住的紀錄，報告應寫明預測的是資料集定義下的取消／未入住，不能默默當成「客人在抵達前主動取消」。

11/4 曾做抵達年度切分的模型實驗：梯度提升樹 ROC-AUC 約 0.872，經驗規則約 0.748；較窄個人訂單範圍約 0.813。**本次沒有重跑模型；這些是先前原型實驗，不是本次新成績，也不是上線驗收。**

### 3.4 四個足以讓結論失真的風險

| 風險 | 為什麼會影響結論 | 本組應怎麼處理 |
|---|---|---|
| 結果洩漏 | `reservation_status` 與 `reservation_status_date` 含結果資訊 | 不作模型特徵；只在離線標籤與稽核中使用 |
| 特徵時間不明 | 訂單修改次數、分房、需求、房價、人數等可能是更新後的值 | 建特徵可用時間表；保守組合為主，完整組合只作敏感度比較 |
| 訂單看起來重複 | 31,994 列與前列完全相同，但沒有 booking ID | 不直接稱為重複訂單；原列與去重敏感度分開報 |
| 政策及通路支配模型 | 不退款類別的取消率反常地高；訂金欄由抵達／取消前付款交易推導 | 主模型先排除此欄，擴充版才作敏感度比較；關聯不能當因果或政策建議 |

原研究盡量使用抵達前一天的資料版本，不等於所有欄位都是初次下訂值。把抵達日減 `lead_time` 算出日期，也不能把更新後欄位還原成當天的狀態。

其中 `deposit_type` 不是單純的取消政策：論文以抵達／取消前的付款交易判定；`ADR` 也以住宿交易金額與晚數計算。兩者都不能直接認定是預訂當下已知資訊。ADR 可在回溯金額描述中使用，未證明當時可取得前不放進預訂時點的保守模型。

本次重算也發現：若把 **2017-01-01** 當模型凍結日，抵達年份早於 2017 的訓練列仍有 **393 列**最後狀態在凍結日當天或之後；2017 抵達的測試列中，**14,122 列**的近似建立日早於凍結日。後者日期只由抵達日減提前天數推導，PMS 建立日也不一定等於客人最早下訂日。這直接說明「依抵達年度切分」不能宣稱是嚴格的新訂單上線測試。

**因此要修正先前 T1 開場「只用訂房當下的欄位」的強說法：那是候選欄位的設計意圖，並未由逐筆事件紀錄證明。**

### 3.5 最小可辯護的實驗

1. 先寫資料契約：一列代表什麼、目標如何定義、打算何時評分、哪些資訊必須當時已知。把「歷史研究」與「未來部署流程」分開。
2. 做兩套特徵：保守組合與擴充組合。連可能變動的房價、住晚數與客人歷史資訊都需註記可用時間，不能只刪答案欄就宣稱無洩漏。
3. 保留最晚一段作最終測試；訓練內另用較早／較晚期間選模型與門檻。既有抵達日切分可作可重現基準，但**不是完整模擬上線時序**。
4. 若推導預訂日做近似時間切分，須說明抵達日與提前天數可能經過更新；且訓練標籤必須在測試評分起點之前已揭曉。無法建立這點時，只能稱回溯分析。
5. 比較整體取消率基準、簡單規則、邏輯迴歸、一個樹模型。補值、編碼與門檻都只用訓練／驗證資料決定。
6. 主要報 PR-AUC、ROC-AUC、校準與 Precision@K／Recall@K。K 由每天人工可處理量決定；不要只用準確率。
7. 同時報兩家酒店及主要客群；另比較去重、移除訂金欄及保守特徵版本，避免靠單一容易類別撐高總分。
8. 本組訂的最低通過標準：同一最終測試範圍、同一 K 下，模型的名單命中率優於簡單規則；若校準不穩就顯示風險等級，不把分數當可信機率。門檻與結果都須記錄，不能看完測試再修改目標。

這個標準是專案驗收設計，不是老師規定；沒有預先承諾某個 AUC 或「降低取消 20%」。

### 3.6 金額與挽留效果怎麼講才成立

`ADR × 住宿晚數` 可作預訂房費暴露的近似量，須先處理零晚數、負價與極端值；不包含完整費用、退款、已收訂金與再售收入。被取消的預訂房費不是等額實際損失。

首版以「有限跟進名單覆蓋多少歷史取消及其預訂房費」為主。若要估算效益，另列假設的挽留成功率、房間無法再售比例、貢獻毛利與聯絡／優惠成本，做低中高情境；標題必須寫「情境試算」。沒有干預紀錄或對照試驗，不能把試算寫成真實節省。

### 3.7 AI 層最小設計與驗收

輸入只包含風險結果、可信的訂單欄位與團隊明確編寫的政策文件；模擬政策必須標明。輸出固定三項：風險相關因素、建議確認事項、聯絡草稿。人工確認後才可採取行動。

不允許 AI 編造客人取消原因、保證退款、建議未核准折扣、依國籍差別待遇，或把特徵相關性寫成客人的真實意圖。不依模型自動取消、拒單或超售。

先用 20 個去識別案例，涵蓋高／中／低風險、缺值、異常金額及不同訂金條件，由業務角色按清單檢查：是否有事實根據、是否符合政策、是否可執行。20 筆只是早期品質試驗，不能推導真實挽留率；任何政策或金額捏造都算未通過，修正後重驗。另比較固定模板，確認 LLM 是否確實改善易懂性或編輯時間。

## 4. 四人如何分工，避免最後只剩 Kenny 做模型

沿用目前已確認的職責，不把背景代號直接當成職責分配：

| 職責 | 酒店方向的實際產出 | Airbnb 方向的實際產出 |
|---|---|---|
| 專案負責 | 範圍、里程碑、風險及需求追溯；整合 AT2 | 城市與房源範圍、資料版本與排除準則 |
| 開發 | CSV 輸入、名單與訂單詳情介面、模型接入、人工確認流程 | 篩選器、可比房源、聚合地圖與解釋介面 |
| Kenny：數據分析＋開發 | 資料品質、特徵時間表、基準與評估、結果接入 | 缺值偏差、價格基準、誤差與跨期分析 |
| 報告呈現／業務理解／利害關係人 | 預訂主管流程、K 與政策、AI 草稿驗收、效益假設 | 房東決策、可比條件、定位文案與限制驗收 |

每人應留需求、決策、評估或交付證據，各自說得清楚自己的內容。業務角色要參與驗收，不能只在最後美化投影片；開發角色要能獨立展示完整流程。

## 5. 最小執行路線與定題門檻

| 期間（台灣日期） | 必須拿到的證據 |
|---|---|
| 11/7–11/10 | 酒店原檔及字典固定；特徵時間表；20 筆 AI 試驗；若偏好 Airbnb 則先驗證價格缺值與可比樣本 |
| 11/11–11/15 | 組會定題，完成業務目標、分析任務、基準及驗收設計；不要把本研究當成已決議 |
| 11/16–11/22 | AT2 架構、實驗設計與風險表；確認現場簡報時段 |
| 11/23–12/11 | 計畫稿與小型端到端展示，加入簡報回饋並交 AT2 |
| AT2 後至 AT3 | 擴充實驗、完成介面與 AI 驗收，整合業務情境與部署限制；假期及個人可投入時間由組會排定 |

酒店定題前應過三個門：資料可重現、模型與時序限制講得清楚、AI 草稿能按政策通過早期測試。若 AI 不通過，先降為可解釋的風險與人工跟進原型，並重新評估 AT3 技術創新的呈現，不硬加未驗證功能。

Airbnb 定題前則應確認：願意研究價格定位而非取消、有效價格樣本足夠、可比房源基準有用。若核心需求仍是取消預測而無交易資料，就停止該方向。

## 6. 組會可以採用的目標草稿

**酒店總目標：**設計並評估一個以公開歷史酒店預訂資料為基礎的取消風險與人工跟進原型，在有限跟進資源下提供可解釋的優先名單與符合政策的聯絡草稿。

具體目標：建立可重現的資料品質與時間語義檢查；以同一測試範圍比較基準和模型；展示固定處理量下的排序表現與校準限制；完成互動介面；由業務角色檢查 AI 草稿並揭露效益情境假設。

**Airbnb 總目標：**利用雪梨公開房源快照，設計並評估房源價格定位與市場比較助手，協助房東理解標價相對同類房源的位置與主要相關因素。

具體目標：檢查價格缺值與樣本覆蓋；定義可比房源；建立中位數基準與標價模型；呈現分群誤差與資料限制；評估解釋是否幫助使用者完成定位任務。公開資料不足以驗證收益提升與取消降低。
