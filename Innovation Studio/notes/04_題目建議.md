## 我的推薦

### 首選:T1 車輛缺陷早期預警雷達

1. **評分點最好打**。投訴檔有里程、車速、撞車/起火/受傷欄位 → AT2 要的分布和相關性好做。真實召回日期可以當「答案」做回測。有前沿方法可以重現:Jones 等人(ESV26-289)在 GM 點火開關案,24 款召回車有 19 款事前就偵測到,平均早 7.43 年。還能誠實比「LLM 有沒有贏過傳統分類」。
2. **最貼你**。幾乎就是你平常的工作換成公開資料:車用 AI 產品測試、分析問題回報找根因、AI 車隊影像平台 PM。直接對到你調查寫的「優化客訴或產品管理」。痛點講得出來,AT2 簡報和 AT4 口試最好答。
3. **最好招人、資料最穩**。美國政府公開、免帳號免 key、每天更新。「召回前就亮燈」的故事好講;3 位評審給的招人分最高(4.3)。11/4 前不用下載,用 API 畫一張「投訴趨勢＋召回日」就能拿去招人。

**主要風險**:範圍太大,加上回測容易偷看未來。
**對策**:MVP(最小可用版本)只做 2020 年後、3–5 個品牌或 2–3 個零件群組。回測一律用 NHTSA 收件日(LDATE),排除召回後才產生的投訴(來源碼 RC/RP/DP 等)。成功標準不寫「預測召回」,改寫「提早提示待查訊號、幫工程師排優先順序」。API 實測 14 次有 4 次逾時 → 批次分析用下載檔,demo 全部預先快取。

### 次選:T3 自駕事故 → 測試場景產生器

1. **最好做完**。資料就是一個約 2.8 MB 的 CSV,原構想階段已實際下載統計過,筆電就能跑,LLM 費用極低。3 位評審「做得完」都給滿分。
2. **最用得到你的測試驗證專長**。「現場問題 → 測試案例 → 覆蓋率」是你最熟的鏈。檔案裡的結構欄位可以直接當 LLM 萃取的自動答案,不用全靠人工標。
3. **題目新、課堂少見**。自駕＋真實事故＋LLM;有 2025 年的事故分群論文和 CVPR 2024 的 ChatScene 可當前沿參考;demo 可以現場產生一條測試案例。

**主要風險**:資料小又偏。單一公司約佔八成、約四成是自車停著被撞、行人等用路弱勢者很少 → 相關性分析和社會面容易單薄。自己編「現有測試計畫」會被說是循環論證。
**對策**:併入 2021–2025 舊版檔(樣本約 3,800 筆,估計);主分類改成 10–12 類;用 CARLA 公開情境清單當「現有測試計畫」。

### 怎麼二選一

- T1 和 T3 用同一個資料來源單位(NHTSA),**只做一個**。
- 想要「客訴」主軸＋最強的 HD 故事 → **T1**。
- 招不到很會寫程式的隊友、想穩穩交出能跑的系統 → **T3**。
- T1 招不到程式強的人也有退路:縮成「預警雷達＋LLM 摘要」,拿掉 RAG。

## 第 1 名｜T1 車輛缺陷早期預警雷達(平均 26.7)

**評審一句話**:8 題中 HD 潛力最高、最貼 Kenny;但零件最多,範圍一定要砍。

### 業務情境

- **企業是誰**:車廠或一階零件供應商(Tier-1,直接賣零件給車廠的大廠)的市場品質(field quality,車子賣出去之後的品質)團隊。經理看結論,品質工程師看細節。
- **痛點**:每週品質會議前,工程師人工讀投訴、用 Excel 計數。同一個問題被分到不同零件、重複回報、嚴重度看人。訊號埋在雜訊裡;越晚發現,召回越大。
- **目標對照**(BO = 業務目標、AG = 分析目標、T = 任務;範例,AT2 再定稿):
  - BO1 縮短「異常出現 → 內部立案」的時間 → AG1 每週偵測「車型×年份×零件」投訴異常 → T1 計數＋異常分數,用歷史召回回測。
  - BO2 減少工程師讀投訴的時間 → AG2 把敘述轉成可篩選欄位(失效模式、觸發情境、警示燈、嚴重度)→ T2 LLM 結構化萃取＋人工抽檢 200–300 筆。
  - BO3 讓升級決策有證據 → AG3 新訊號自動比對已有召回與調查 → T3 RAG,每句附編號。
- **成功標準**(起點,回測後再調):
  - 業務語言:工程師每週要讀的投訴少 80%;重大問題比現在更早立案。
  - 數字指標:用 2020–2024 召回回測,≥ 60% 的召回在 NHTSA 收件日前 90 天以上就亮燈(Jones 等人也承認很多召回事前沒有投訴高峰,這個門檻可能要下修);每週前 20 張警示至少一半值得查(precision@20 ≥ 0.5,也就是前 20 張裡真的有問題的比例)。

### EDA 可以看什麼

- **分布**:每月投訴量(看季節性、新車或軟體更新後的跳升);里程 MILES(右偏 → 取對數,依零件畫箱型圖,看是早期故障還是磨耗);車齡 = 收件年 − 車款年;通報延遲 = 收件日 − 事發日(2018 Accord 抽樣:中位數 13 天、P90 338 天,長尾);受傷/死亡極少(同一抽樣:撞車 1.8%、起火 0.2%),寫成「罕見但嚴重」;零件前 20 名;召回受影響車數(重尾)。
- **相關性**:零件 × 撞車/起火的列聯表＋卡方檢定＋Cramér's V;車速 vs 是否受傷(點二系列相關或邏輯迴歸);里程 vs 車齡(Spearman);「召回前後 12 個月投訴量」事件研究圖(event study),直接回答「為什麼要做預警」。
- **資料品質**:同一件投訴有多個零件會重複出現 → 先用 ODINO 去重;2021-05 系統更新後空白數字變 0 → MILES = 0 當缺值,時間序列在 2021-05 有斷點。

### 方法:基準(baseline) vs 前沿 AI

全部依時間切分(例如 2015–2021 開發、2022–2025 測試),防止偷看未來。

| 實驗 | 基準(baseline) | 前沿 AI | 怎麼算贏 |
|---|---|---|---|
| A 投訴分類 | TF-IDF(把文字轉成數字的老方法)＋邏輯迴歸、LightGBM(常用的樹模型) | 句向量＋分類器、SetFit(少量標註就能訓練,CPU 可跑)、LLM few-shot 結構化輸出 | macro-F1、各類 recall、每千筆成本與秒數 |
| B 預警 | 固定門檻(月量 > 平均＋3 個標準差)、EWMA(近期權重較高的移動平均) | 重現 Jones 等(ESV26-289)的 Cohen's d(兩組差幾個標準差)＋滾動 180 天檢定;再加「先用 LLM 分失效模式,再偵測」 | 召回偵測率、提前天數中位數、precision@k、每週警示數(太多會沒人看) |
| C 調查建議單 | 人工寫 | RAG,每句附召回或投訴編號 | 引用正確率、人工盲評(正確、完整、可行動) |

- **金標**:人工標 300–500 筆失效模式,先算兩人一致率(Cohen's kappa)。
- **誠實對照**:Dhillon & Torresin(2024,Chalmers 碩士論文)用 Claude v2 測 NHTSA 投訴,結論是傳統分類器整體較好(已核對)→ 你們驗證新一代 LLM 會不會翻盤。「LLM 不一定贏」本身就是有說服力的實驗。
- **背景文獻**:Jones、Kempegowda、Krivo & Ng(ESV26-289,已核對全文);Abrahams 等(2012)Decision Support Systems 54(1):87–97;Abrahams 等(2015)Production and Operations Management 24(6):975–990;Shi, Qu & Liu(2024)MSI 工作論文 24-102(後 3 篇這次核對沒查,引用前再確認)。

### AT3 系統長什麼樣

- **資料介面**:定期下載分年檔 → 第一步刪個資欄 → 存 Parquet/DuckDB(筆電跑得快的檔案格式/單機資料庫);「查一台車」即時打 API(先快取、加重試)。
- **分析介面**:LLM 失效模式萃取(JSON 固定欄位、temperature 0 讓每次回答一樣;填零件細項、失效模式、觸發情境、嚴重度 1–5、是否涉及軟體/ADAS);每週滾動 180 天異常分數,起火/撞車/受傷加權;召回比對 RAG(查不到就說查不到)。延伸:用自然語言問資料(text-to-SQL,把問題轉成查詢)。
- **使用者介面**(Streamlit,用 Python 做網頁的工具;三頁):①本週警示看板:依嚴重度排序,每張卡有趨勢小圖、件數、是否已有召回 ②警示詳情:LLM 摘要、里程直方圖、代表投訴原文、相似召回 ③查一台車:輸入品牌/車型/年份。
- **可行動按鈕**:「開調查/持續觀察/標記已知問題」→ 一鍵匯出附證據的調查建議單(Markdown/CSV,可貼 Jira);決定存成紀錄(人機迴圈 human-in-the-loop:人做最後決定,系統記下來)。
- **Demo 3 步**(「時光倒流」劇本):
  1. 把系統日期設在某次真實召回前 6–12 個月,請觀眾猜「會不會亮燈、早多久」。
  2. 打開那張警示卡:看 LLM 摘要和代表投訴,按「產生調查建議單」。

### EDA 可以看什麼

- **分布**:自車撞前速度(很多是 0)、最高傷害等級、撞到什麼、道路類型、自車/對方撞前動作、事故時段、州/城市、天氣與撞擊位置多選欄。
- **相關性**:自車速度 × 傷害等級(Spearman 或序位邏輯迴歸);道路類型 × 自車動作(列聯表熱力圖);撞擊位置共現熱力圖;撞到什麼 × 傷害(卡方/Cramér's V;格子太小就合併類別,或用 Fisher 精確檢定,這是樣本很少時用的檢定)。
- **不要做**:「是否在設計運作範圍內」(Within ODD?)幾乎全是 Yes(抽查 275 筆有 273 筆),不能做相關;用路弱勢者 × 傷害格子太小(抽查 387 筆只有 7 筆,行人 1 筆)→ 改成描述性的「少數但嚴重」個案。
- **資料品質**:去重(先每個 Report ID 取最大版本,再用 Same Incident ID 合併不同公司對同一事故的報告);Unknown/Other 比例;日期只到年月、經緯度被遮 → 時序只到月份＋時段,地圖只到城市。

### 方法:基準(baseline) vs 前沿 AI

| 實驗 | 基準(baseline) | 前沿 AI | 怎麼算贏 |
|---|---|---|---|
| A 欄位萃取 | 關鍵字/規則(regex)、TF-IDF＋邏輯迴歸 | LLM zero-shot、few-shot＋自我檢查 | 對既有結構欄位的正確率與 macro-F1;「Unknown」有沒有判成未知 |
| B 情境分類(主戰場) | TF-IDF＋邏輯迴歸 | LLM few-shot(把 37 類描述放進提示) | 200 筆金標的 macro-F1,先算 kappa |
| C 分群 | Palit, Kumarasamy & Osman(arXiv 2512.22589):2,500 多筆 NHTSA L2/L4 事故做 K-means 4 群＋關聯規則 | 加入 LLM 從敘述抽的特徵再分群 | 人工可解釋性評分、輪廓係數(silhouette,分群分得開不開) |
| D 測試案例品質 | 人工撰寫 | LLM 產生 Given-When-Then | Kenny 設計的 rubric(可執行、參數完整、通過標準可量測、和原事故一致)2 人盲評;人工修改比例、省下的時間 |

- **注意**:Waymo 的敘述句型很制式 → 規則基準在實驗 A 可能就很強。LLM 的價值押在實驗 B、D,不要把 A 當主賣點。
- **答案要排除**:「Other, see Narrative」「Unknown」不能當自動答案。
- **前沿參考**:ChatScene(Zhang, Xu & Li, CVPR 2024)用 LLM＋知識檢索產生自駕安全關鍵場景;你們做前半段(事故文字 → 結構化場景),不用 GPU。

## 第 4 名｜T5 Bug 回報去重 Copilot:讓 QA 少讀約五分之一的重複單(平均 23.0)

**評審一句話**:實驗設計最乾淨(有現成答案、有現行工具可以比),最用得到你的 bug triage 經驗;但「客訴」味淡、社會面偏弱。

### 業務情境

- **企業是誰**:軟體/App 產品團隊(也適用手機、IoT 韌體)的 QA 主管、分流(triage)工程師、客服。
- **痛點**:每週分流會議要看大量新回報。用 Bugzilla 即時計數,2020–2024 年 Firefox 約 18.6%、Thunderbird 約 22.1% 的缺陷回報最後被標成「重複」→ 約五分之一的閱讀時間花在重複單。回報又常缺重現步驟和版本。
- **目標對照**:
  - BO1 減少 triage 人工時間 → AG1 新回報進來就找出重複候選(前 k 名)→ T1 句向量檢索＋LLM 重排。
  - BO2 縮短回報到修好的時間 → AG2 建議元件/優先級、找相似已修案例 → T2 分類模型＋RAG(延伸)。
  - BO3 提升回報品質 → AG3 檢查缺漏、產生追問草稿 → T3 LLM 結構化萃取(延伸)。
- **成功標準**(起點):
  - 業務語言:triage 工程師每週少讀約五分之一的重複單;新單幾秒內就知道「以前有沒有人報過」。
  - 數字指標:依時間切分的測試集上 Recall@5 ≥ 0.6,而且要贏過 Bugzilla 內建工具;每筆查詢 < 5 秒。

### 資料(10/29 核對)

1. **GitBugs(GitHub)**
   - 連結:<https://github.com/av9ash/gitbugs>;資料集論文 <https://arxiv.org/abs/2504.09651>(v4,2026-04-28)。
   - 大小:repo 約 47 MB;9 個專案,README 加總 192,387 筆回報。MVP 用 Firefox(壓縮 12.25 MB,24,824 筆)＋Thunderbird(14.15 MB,15,192 筆);查證時用 Bugzilla 即時計數交叉核對,筆數可信。
   - 範圍:單一產品、只有 defect(缺陷)、2020-01-01 到約 2025-03-05。
   - 欄位(8 欄):Summary 標題、Issue id、Status、Priority、Resolution、Created、Resolved、Description 描述;另有配對檔(Issue id ↔ Duplicate id)。沒有元件、嚴重度、版本(用 API 補)。
   - 授權:README 寫 CC BY 4.0,但 repo 沒有 LICENSE 檔;底層文字是 Mozilla 貢獻者寫的 → 報告寫「CC BY 4.0(依 README 聲明)」,不要整包再散布。
   - 怎麼下載:`git clone`,不用帳號。
2. **Mozilla Bugzilla REST API**
   - 連結(Firefox 重複單範例):<https://bugzilla.mozilla.org/rest/bug?product=Firefox&resolution=DUPLICATE&limit=2&include_fields=id,summary,component,dupe_of,creation_time>;文件:<https://bmo.readthedocs.io/en/latest/api/core/v1/bug.html>
   - 欄位:id、summary、component 元件、severity 嚴重度、priority、status、resolution、dupe_of(重複到哪張主單,一對一,比配對檔乾淨)、creation_time。
   - 現行工具基準:內建 `/rest/bug/possible_duplicates` 匿名可用。
   - 新鮮資料:查證時抓得到 2026-10-22 當天建立的新 Firefox bug → demo 可以抓當天新單。
   - 授權:API 文件沒寫資料授權 → 只用公開 bug、學術用途、註明來源並連回原單。
   - 怎麼下載:匿名 GET 就回 JSON。每個 IP 有速率限制(先回 400、再回 429);留言 JSON 會帶回報者 email → 不存、不送 LLM。

- **目標對照**:
  - BO1 縮短每份報告的分類時間 → AG1 自動多標籤編碼(異常類型、主要問題、肇因、人為因素),而且和專家一致 → T1 LLM 編碼＋拿 NASA 專家碼評估。
  - BO2 及早發現新危險 → AG2 每季找出成長中的事件群 → T2 句向量分群＋趨勢。

- **成功標準**(起點,已依核對修正):
  - 業務語言:安全分析師讀 20 份報告,有系統比沒系統快 50%。
  - 數字指標:三欄 micro-F1 ≥ 0.75(自訂門檻,沒有文獻依據),一定同時報 macro-F1 和每類 F1;稀有類 recall 附 bootstrap 信賴區間(重抽樣算出的誤差範圍),或把稀有類併成大類。

### EDA 可以看什麼

## 第 6 名｜T4 客服第一線 Copilot(平均 20.0)

**評審一句話**:最直接對到你寫的「優化客訴」,介面最像真產品;但資料是 2017 年推特、大約只有 2 個月、完全沒有標籤,又是 Kaggle 常見題。

### 業務情境

- **企業是誰**:手機、電腦、電信品牌的社群客服主管、第一線客服、產品/QA 窗口。
- **痛點**:尖峰時客訴暴增,主管要決定先回誰、是不是有新 bug 在擴散、要不要通知產品團隊。客服和 QA 用語不同,同一個 bug 很多種說法。新人回覆品質不一。
- **背景文獻(注意版本)**:Brynjolfsson, Li & Raymond〈Generative AI at Work〉。NBER 工作論文版(w31161,2023):5,179 位客服導入生成式 AI 助理後,每小時解決問題數 +14%、新手 +34%。已刊 QJE 2025, 140(2):889–942 的摘要寫 5,172 位、+15%。引用哪一版就用哪一版的數字,不能混(34% 要查 QJE 全文再引)。
- **目標對照**:
  - BO1 縮短首次回應時間(FRT)、降低服務時限(SLA)違約 → AG1 自動分類意圖、產品、緊急度、要不要轉技術 → T1 LLM 分流器。
  - BO2 讓 QA 更早收到新問題 → AG2 主題分群＋每日量異常偵測 → T2 新問題雷達＋缺陷回報草稿。
  - BO3 提高回覆品質與一致性 → AG3 找相似歷史對話 → T3 RAG 回覆草稿,由客服送出。
- **成功標準**(起點):
  - 業務語言:緊急客訴先被回;新問題爆量時 QA 當天就知道。
  - 數字指標:分流 macro-F1 ≥ 0.8、緊急類 recall ≥ 0.9(AT2 前先標 200 筆,AT3 再補到 500–1,000 筆);回覆草稿人工評分「可直接用或小改」≥ 70%;新問題雷達在人工事件清單上平均提早 ≥ 1 天。

## 附錄:名詞小抄

| 名詞 | 白話 |
|---|---|
| LLM | 大語言模型(像 ChatGPT、Claude) |
| RAG | 先查資料,再讓 LLM 根據查到的內容回答,並附出處 |
| EDA | 先畫圖、算統計,看資料長怎樣 |
| 基準(baseline) | 拿來比的簡單方法;前沿方法要贏它才算數 |
| 回測(backtest) | 假裝回到過去,只用當時有的資料,看系統準不準 |
| 資料外洩(leakage) | 不小心用到「未來才知道」的資訊,分數會灌水 |
| 金標 | 人工標好的標準答案,拿來考模型 |
| 句向量(embedding) | 把一段文字變成一串數字;意思越像,數字越近 |
| zero-shot / few-shot | 不給範例 / 給幾個範例,就叫 LLM 做事 |
| 結構化輸出(structured output) | 規定 LLM 一定要照固定欄位(JSON)回答,程式才接得住 |
| precision / recall | 抓到的裡面有幾成是對的 / 該抓的裡面抓到幾成 |
| macro-F1 | 每一類各算一次分數再平均,小類不會被大類蓋掉 |
| precision@k | 排名前 k 個裡面,真的有問題的比例 |
| Recall@5 / MRR | 正確答案有沒有出現在前 5 名 / 正確答案平均排多前面(越前越高) |
| Cohen's kappa | 兩個人標註的一致程度(扣掉碰巧一樣的部分) |
| Cramér's V | 兩個類別欄位的關聯強度(0 = 沒關係,1 = 完全相關) |
| Spearman | 兩個數值欄位的排名相關 |
| 點二系列相關 | 一個「是/否」欄位和一個數值欄位的相關 |
| MVP | 最小可用版本:先做出能跑的核心,再加功能 |
| OTA | 遠端軟體更新(不用回廠) |
