```python
import csv, datetime as dt
from pathlib import Path
with Path('scratchpad/hotel1107/hotels.csv').open(encoding='utf8', newline='') as f:
    rows = list(csv.DictReader(f))
months = {m: i for i, m in enumerate('January February March April May June July August September October November December'.split(), 1)}
arr = [dt.date(int(r['arrival_date_year']), months[r['arrival_date_month']], int(r['arrival_date_day_of_month'])) for r in rows]
book = [a-dt.timedelta(days=int(r['lead_time'])) for r, a in zip(rows, arr)]
cut = dt.date(2017, 1, 1)
assert (len(rows), len(rows[0])) == (119390, 32)
assert sum(r['is_canceled']=='1' for r in rows) == 44224
assert len(rows)-len({tuple(r.values()) for r in rows}) == 31994
assert sum(a<cut and dt.date.fromisoformat(r['reservation_status_date'])>=cut for r,a in zip(rows,arr)) == 393
assert sum(a>=cut and b<cut for a,b in zip(arr,book)) == 14122
```

## 3. 會改變可行性判斷的資料限制

### 3.1 「取消預測」可做，但時間點不能亂說

原論文把資料時點定在抵達前一天，盡可能回查變更紀錄；另提醒人數、晚數、房型、國籍可能到入住或住宿期間才更正。公開檔不是完整事件流水，也不是每次下訂的原始快照。

| 欄位 | 原文定義／風險 | 最小處理 |
|---|---|---|
| `reservation_status`、`reservation_status_date` | 最後結果及日期，直接揭露答案 | 不作模型特徵；日期僅供標籤成熟、切分與回溯分析 |
| `booking_changes` | 累積至入住或取消的變更次數 | 刪除；不能當下訂時可用特徵 |
| `deposit_type` | 原文按交易表中「抵達或取消以前」實付金額推導分類 | **不是單純下訂時退款政策**；保守模型刪除，擴充模型單獨揭露 |
| `adr` | 原文由住宿交易總額除以住宿晚數計算 | 不能保證是下訂報價；保守模型先排除，不把它當已知收入 |
| `assigned_room_type`、車位、特殊需求 | 可能跟營運、後續更新或到店狀態有關 | 保守模型先排除；不得說每筆一定是入住後填寫 |
| `country`、人數、晚數、預訂房型 | 有些雖原理上下訂會知道，但公開版本可能已更新 | 書面列假設；不能把欄位名稱當成時間可用性的證據 |
| `days_in_waiting_list` | 確認訂單前的等候天數 | 若定義「確認後評分」才可能可用；不適合直接當剛建單即時值 |

**推論**：刪除明顯洩漏只能降低風險，不能從這份公開檔證明完整的預訂當下可用性。要驗證真實即時預測，仍須酒店提供帶時間戳的建立、變更、取消紀錄。

### 3.2 原本時間切分仍有穿越問題

- 既有 T1 用抵達日切分：2016 年以前抵達 78,703 筆訓練；2017 年抵達 40,687 筆測試。這是「抵達年份留後測試」。
- 本次重算：以 **2017-01-01** 為假定凍結日，前一組有 **393 筆**最後狀態日期仍在凍結日當天或之後；當時不能一律視作已知標籤。
- 本次重算：後一組有 **14,122 筆**的估計建立日早於凍結日。估計建立日＝抵達日−`lead_time`，原定義是 PMS 建立日，不一定等於客人最早下訂時間。
- 因此不能把「2017 年抵達」直接寫成「2017 年新下訂」；也不能把 AUC 當作按當時可用資料前向部署的證明。
- 修正方案：凍結日只訓練最後狀態已在之前成立的列；測試改用凍結後估計建立的訂單；在更早期間做驗證與選門檻。這仍是日期層級近似，非事件時間還原。
- 若做「入住前 7 天待處理名單」，必須先排除該日以前已取消的列；公開檔缺完整 D−7 特徵，該示範只能標成回溯原型。

### 3.3 高分與商業可用不是同一件事

- 完全相同列可能是多間相同團體房，直接刪除會改變樣本母體；主表保留，另報去重敏感度版本，並避免相同特徵組跨訓練／測試。
- `market_segment=Groups` 與 `customer_type=Group` 定義不同，不能合併解釋；「非退款團體單」亦不等於已證實不能挽留。
- 國籍、旅行社／公司代碼可能強烈標識這兩家酒店的業務結構；另報移除國籍及匿名機構代碼的結果，避免以國籍直接決定拒單或差別待遇。
- 沒有客人 ID，不能嚴格證明新客戶泛化；沒有聯絡、折扣、補售或干預結果，不能驗證「聯絡造成少取消」與實際營收提升。
- `取消機率×ADR×晚數` 最多是帶假設的名目風險排序；不是預期淨損失，更不是預期挽回收益。

| 舊結果 | 可支持什麼 | 不能支持什麼 |
|---|---|---|
| 梯度提升樹 ROC-AUC 0.872；規則 0.748 | 這份資料存在可學習訊號；值得做原型 | 已證明預訂當下或今天酒店的準確率 |
| 原定義個人訂單子集 AUC 0.813；最保守特徵組 0.790 | 較難子集與特徵選擇會影響成績 | 這些分數已通過本次更嚴格切分 |
| 隨機切分 AUC 0.944 | 評估方式影響很大，需報切分規則 | 所有差異都一定來自重複列洩漏；隨機切分沒有驗證未來表現 |

舊筆記「只用下訂當下欄位」應降格為「按當時選定的較保守欄位」；舊目標如 AUC≥0.88 應待切分修正後重新設定。

## 5. 最小而完整的分組專案

**建議題名**：酒店訂單取消與未入住風險排序及決策支援原型。

**Aim 草稿**：協助酒店訂房人員在有限處理量下，優先檢視較高取消或未入住風險的訂單，提供可追溯的風險依據與人工覆核清單。

**Objectives 草稿**：

1. 完成資料來源、標籤、時間可用性與清理規則；分開定義「原始取消＋未入住」和「僅主動取消」。
2. 建立常數機率／簡單提前天數規則、邏輯迴歸及一個梯度提升樹，所有前處理只在訓練集擬合。
3. 用較早期間驗證、較晚期間保留測試；預先固定處理量（例如前 20%），比較 ROC-AUC、PR-AUC、precision@20%、recall@20% 與 Brier 分數。
4. 報兩酒店分開、全量／去重、移除訂金／國籍／機構代碼的敏感度結果；把資料時點限制寫進結論。
5. 做一個批次評分清單：匿名列號、分數、可驗證欄位、人工覆核動作；以小型任務測試確認非技術成員能理解。

- **成功標準**：修正切分後優於預先固定的規則；處理量與門檻在驗證期選定，測試期只評一次。幅度目標待新基準建立後由團隊預先登記，不承諾一定拿到 0.88。
- PR-AUC／命中率需並列該測試集取消比例；不同切分的數字不能直接拿來說進步。
- 任何「收益」只做明示挽回率、補售率、毛利與聯絡成本的情境分析；沒有干預資料，效果保留未知。

### AI 文字層：可以加，但不當核心阻塞

- 先用固定模板產生兩三句說明即可完成決策支援；生成式 AI 可作擴充比較。
- 若使用 LLM，只餵模型輸出與允許欄位，要求引用欄位事實；不自行推測取消原因、客人意圖、政策或優惠資格。
- 在預先抽定的案例集比較模板與 LLM：事實一致性、可理解、是否符合允許行動，由非產出者用同一評分表盲評。
- 小樣本「零錯誤」只能說該樣本未見錯誤，不能宣稱模型永不幻覺；不把 SHAP 關聯貢獻稱作因果原因。

## 6. 選題裁決

- **GO**：以公開資料做可重現的歷史離線評估與人工決策支援原型。資料可立即取得、標籤清楚、已有訊號、四人都有可驗收的工作。
- **條件式 GO**：要聲稱「下訂即時」或「D−7 真正提前預警」，先取得可還原該時點的特徵與結果紀錄；現在只能做帶假設的概念驗證。
- **NO-GO（現有資料無法證明）**：真實挽留成效／保證營收提升、跨酒店直接上線、把此酒店模型當 Airbnb 取消模型。
- 未檢查：未重跑前次模型、未取得酒店合作資料、未申請受限新資料；主要風險仍是時間可用性與真實流程差異。
